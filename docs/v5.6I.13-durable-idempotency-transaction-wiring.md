## Problem: in-process cache ไม่พอสำหรับ multi-instance

Cloud Run หลาย instance แต่ละตัวมี `Map` ของตัวเอง:

```
Instance A                    Instance B
    │                              │
    ├─ POST req-123 (processed)    │
    │  idempotencyCache.set(...)   │
    │                              ├─ POST req-123 (cache miss!)
    │                              │  → duplicate state + audit
```

Durable `settlementIdempotencyRecords` ใน Firestore transaction แก้ race ข้าม instance ได้

---

## Durable transaction design

```
POST /api/admin/revenue/adjustments
        │
        ▼
  resolveSettlementRequestId()
        │
        ▼
  assertWritesAllowed()   ← NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED=true
        │
        ▼
  db.runTransaction(async tx => {
        │
        ├─ READ settlementIdempotencyRecords/{docId}
        │
        ├─ IF NOT EXISTS:
        │     compute next state + audit draft (invariant validated)
        │     build idempotency record { status: "processed", auditLogId, responseSnapshot }
        │     assertNoBuyerPiiInIdempotencyRecord()
        │     WRITE idempotency + settlementAdjustments + settlementAuditLogs
        │
        ├─ IF EXISTS + same payloadFingerprint:
        │     READ state + audit by settlementAdjustmentId / auditLogId
        │     RETURN duplicate (no new audit write)
        │
        └─ IF EXISTS + different payloadFingerprint:
              THROW SettlementAdjustmentIdempotencyConflictError (409)
  })
```

Implementation: `src/server/repositories/settlementAdjustmentRepositoryFirestore.ts`  
Pure decision helper: `resolveDurableIdempotencyTransactionOutcome()` in `durableIdempotencyModel.ts`

## Duplicate / replay behavior

| กรณี | HTTP | ผล |
|------|------|-----|
| Same docId + same `payloadFingerprint` | 200 | `idempotency.outcome: "duplicate"` — คืน state/audit เดิมจาก Firestore |
| New docId | 200 | `idempotency.outcome: "processed"` |

Replay ใช้ `auditLogId` + `settlementAdjustmentId` จาก idempotency record — **ไม่ append audit ซ้ำ**

---

## Conflict behavior

| กรณี | HTTP | ผล |
|------|------|-----|
| Same docId + different `payloadFingerprint` | 409 | `SettlementAdjustmentIdempotencyConflictError` |

## Fail-closed behavior

| กรณี | พฤติกรรม |
|------|----------|
| Transaction fail | Error propagate — **ห้าม** บอก admin ว่าสำเร็จ |
| `NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED!=true` | `assertWritesAllowed()` throw ก่อน transaction |
| Idempotency record มี แต่ state/audit หาย | throw `"idempotency record corrupt"` |
| Backend=firestore | **ห้าม** silent fallback เป็น memory |

## No PII responseSnapshot

`redactIdempotencyResponseSnapshot()` เก็บเฉพาะ:

- `outcome`, `settlementStatus`, `feeAmount`, `paidAmount`, `remainingAmount`, `auditLogId`

**ห้ามมี:** buyer phone, email, contact, owner phone, buyer name

Validation: `assertNoBuyerPiiInIdempotencyRecord()` ก่อน `tx.set(idempotencyRef, ...)`

## Rollback plan

1. ปิด `NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED` → repo throw ก่อน write
2. สลับ `NONGA_SETTLEMENT_DATA_BACKEND=memory` → runtime กลับ memory
3. Revert Firestore repo commit → กลับ in-process cache (ไม่แนะนำหลัง enable)
4. Idempotency docs ค้างใน Firestore — ไม่กระทบ memory runtime
5. Rules deny-all ยังป้องกัน client access
