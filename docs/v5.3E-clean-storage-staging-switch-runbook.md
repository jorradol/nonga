## Rules Readiness

Firestore:

- `firestore.rules` and `firestore.rules.draft` match.
- The current Firestore rules include the collections needed by the repository-backed dealer flow:
  - `dealerListings/{listingId}`
  - `dealerDrafts/{draftId}`
  - `listingImages/{imageId}`
  - `users/{uid}`
  - `dealerMembers/{membershipId}`
- Dealer-scoped access checks require an active dealer membership or active admin role.

Storage:

- `storage.rules.draft` covers the expected Firebase Storage paths:
  - `listing-images/{dealerId}/{listingId}/{fileName}`
  - `draft-images/{dealerId}/{draftId}/{fileName}`
  - `chat-attachments/{dealerId}/{sessionId}/{fileName}`
- The draft rules limit writes to authenticated active dealer members/admins and image uploads within the configured size/type checks.
- `firebase.json` currently does not include a `storage.rules` deploy target, so Storage rules are not ready to deploy from the current config without an explicit approved rules/config change.

Important: Cloud Run server-side Firestore and Storage operations use Firebase Admin credentials and bypass client security rules. The rules still matter for client-side reads/writes, future direct Storage access, and defense in depth. Do not deploy rules in V5.3E.

## Commands Prepared, Not Executed

Set an image tag for the approved V5.3F run:

```bash
export IMAGE_TAG=v5.3f-clean-storage-staging
export IMAGE_URI=asia-southeast1-docker.pkg.dev/nonga-ce93c/nonga-staging/nonga-staging:${IMAGE_TAG}
```

Build the Docker image with public Vite build args:

```bash
docker build \
  --build-arg VITE_FIREBASE_API_KEY=<firebase-web-api-key> \
  --build-arg VITE_FIREBASE_AUTH_DOMAIN=nonga-ce93c.firebaseapp.com \
  --build-arg VITE_FIREBASE_PROJECT_ID=nonga-ce93c \
  --build-arg VITE_FIREBASE_STORAGE_BUCKET=<firebase-storage-bucket> \
  --build-arg VITE_FIREBASE_MESSAGING_SENDER_ID=<firebase-messaging-sender-id> \
  --build-arg VITE_FIREBASE_APP_ID=<firebase-app-id> \
  --build-arg VITE_FIREBASE_MEASUREMENT_ID=<optional-measurement-id> \
  --build-arg VITE_NONGA_PUBLIC_SIGNUP_ENABLED=false \
  -t "${IMAGE_URI}" \
  .
```

Push the image:

```bash
docker push "${IMAGE_URI}"
```

Deploy Cloud Run staging only after approval:

```bash
gcloud run deploy nonga-staging \
  --image "${IMAGE_URI}" \
  --region asia-southeast1 \
  --project nonga-ce93c \
  --allow-unauthenticated \
  --set-env-vars NODE_ENV=production,APP_URL=https://nonga-ce93c.web.app,VITE_NONGA_PUBLIC_SIGNUP_ENABLED=false,VITE_FIREBASE_PROJECT_ID=nonga-ce93c,FIREBASE_PROJECT_ID=nonga-ce93c,FIREBASE_STORAGE_BUCKET=<firebase-storage-bucket>,NONGA_DATA_BACKEND=firestore,NONGA_IMAGE_BACKEND=firebase-storage \
  --set-secrets GEMINI_API_KEY=gemini-api-key:latest,FIREBASE_SERVICE_ACCOUNT_JSON=firebase-service-account-json:latest
```

Check Cloud Run health before Hosting deploy:

```bash
gcloud run services describe nonga-staging \
  --region asia-southeast1 \
  --project nonga-ce93c \
  --format="value(status.url)"
```

Then request `/api/health` on the returned service URL and confirm:

- `ok: true`
- `dataBackend: "firestore"`
- `imageBackend: "firebase-storage"`
- `publicSignupEnabled: false`

Deploy Firebase Hosting only after Cloud Run health passes and approval is still active:

```bash
npx -y firebase-tools@latest deploy --only hosting --project nonga-ce93c
```

Never run an unqualified `firebase deploy` for this switch.

## Rollback Plan

If the staging switch fails after V5.3F approval:

1. Keep production untouched.
2. Do not run migration write as a fix.
3. Redeploy or roll back Cloud Run to the previous healthy revision.
4. If only flags need rollback, set:
   - `NONGA_DATA_BACKEND=file`
   - `NONGA_IMAGE_BACKEND=file`
5. Keep `VITE_NONGA_PUBLIC_SIGNUP_ENABLED=false`.
6. Re-run `/api/health`, dealer login, and a short draft smoke.
7. Roll back Firebase Hosting only if the Hosting release caused the break.
