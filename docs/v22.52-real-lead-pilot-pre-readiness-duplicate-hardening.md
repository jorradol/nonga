## 3) Duplicate definition (chosen)

| Rule | Behavior |
|------|----------|
| Active duplicate | Same `buyerUserId` + `listingId` while `queueLifecycle === "active"` → at most one Lead |
| Retry / concurrent | Returns existing Lead; no second queue entry; no second consent contact-log |
| Different listing | Always a distinct inquiry |
| After withdraw/skip | Active slot released → later legitimate inquiry allowed |
| Phone typo while active | Does **not** create a second active Lead (slot is buyer+listing) |

---

## 4) Idempotency strategy

1. Kill Switch checked **before** any repository / slot write.  
2. Soft pre-check via `findActiveDuplicateBuyerLead` (best-effort).  
3. Authoritative: `createBuyerLeadAtomic` — Firestore `runTransaction`:
   - Read deterministic doc `buyerLeadIdempotencyRecords/active-{listingId}-{buyerUserId}`
   - If active + Lead still active → `duplicate` (no writes)
   - Else create Lead + consent contact-log + active slot atomically
4. Skip/withdraw calls `releaseBuyerLeadActiveSlot`.  
5. Contact fingerprint = SHA-256 prefix of normalized phone (stored on slot; **not** raw PII in key).  
6. Memory backend mirrors the same slot semantics for unit tests (not relied on for multi-instance).

Multi-instance safety: Firestore transaction + create-if-absent on deterministic doc id (not process memory).
