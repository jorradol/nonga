## 6. Approval Separation Principle

**Core rule:** Every distinct execution action requires its **own separate approval**. No bundled approval may authorize multiple execution gates.

| Principle | Detail |
|-----------|--------|
| One gate, one approval | Each execution gate has a dedicated approval class |
| No blanket approval | "Approve everything" is forbidden |
| Prior packets ≠ approval | v6.5A–J and v6.4Q–V are planning/boundary only |
| Pre-Commit ≠ Commit ≠ Push ≠ Deploy | Each lifecycle step requires separate owner approval |
| Docs slice ≠ runtime slice | Docs-only approval does not authorize runtime change |
| Staging ≠ production | Staging deploy approval ≠ production deploy approval |
| Pilot start ≠ provider invocation | Starting pilot ≠ invoking Gemini |

**v6.5K captures no approval** — defines separation rules only

---

## 7. Version Boundary Principle

**Core rule:** Each future version type has defined boundaries for what it may contain and what approvals it requires before any action.

| Principle | Detail |
|-----------|--------|
| Version type determines risk | Higher risk = more approval layers |
| New prompt required | Every version slice starts with explicit owner prompt |
| Pre-Commit Report required | Before commit for all version types |
| Separate commit approval | Owner must approve commit explicitly |
| Separate push approval | Owner must approve push explicitly |
| Deploy approval separate | Deploy never bundled with commit/push |
| May Execute Without Separate Approval? = **No** | All version types require separate approval |
