## URL Validation

Implemented fail-fast URL validation before any curl template generation:

- final URL must parse with `new URL(...)`
- protocol allowed only `http:` or `https:`
- hostname must be non-empty
- endpoint path must be exactly `/api/admin/sales-brain-shadow-smoke`
- malformed URL immediately fails as client-side validation failure

## Port Validation

Implemented strict port checks in template helper:

- empty port fails (example `http://localhost:/...`)
- non-decimal port fails (example `http://localhost:abc/...`, `http://localhost:$PORT/...`)
- out-of-range port fails (example `65536`)
- whitespace/quote contamination in base URL fails fast
- decimal port in range `0..65535` is allowed

## Sanitized Curl Command Template

Template helper now returns preview-only sanitized command:

- URL is quoted safely as one shell argument
- `Authorization` header is always masked as `Bearer ***MASKED***`
- payload preview is synthetic (`{"caseId":"SS-01"}`)
- no secret/token/API key value is printed
- no retry flags or retry loop are included

## Status Capture Fix

Client-side capture classification now separates transport/client failure from HTTP response:

- on curl non-zero exit (e.g. `curl exit code: 3`):
  - `http_status: not_available_client_error`
  - `request_dispatched: no_or_unknown`
- on curl success with valid HTTP code:
  - `http_status: <real_3_digit_http_status>`
  - `request_dispatched: yes`
- invalid/non-HTTP artifacts such as `400000` are not accepted as HTTP status

## Request Dispatch Classification

Dispatch classification is explicit:

- `yes` only when curl returns success and a valid 3-digit HTTP status is captured
- `no_or_unknown` for client URL failures, malformed status, or unresolved dispatch evidence

This removes ambiguity between client command construction failure and server/provider behavior.
