# V5.3 Durable Storage Migration Rehearsal Plan

Date recorded: Tuesday May 26, 2026

This document plans the staging-only rehearsal for moving Nong A from ephemeral Cloud Run file storage toward durable Firebase Storage and Firestore. It is a readiness checkpoint only: no migration write, no backend flag switch, no production deploy, no public signup change, and no secrets are recorded here.

## Current State

- Staging URL: `https://nonga-ce93c.web.app`
- Firebase project for staging: `nonga-ce93c`
- Cloud Run service: `nonga-staging`
- Current data backend: `NONGA_DATA_BACKEND=file`
- Current image backend: `NONGA_IMAGE_BACKEND=file`
- Public signup: disabled
- Core closed staging flows passed through v5.1/v5.2: auth roles, Dealer Portal, draft save, publish guard, Chat-to-Draft, new image upload, and `/api/health`.
- Historical `/storage/listings/**` images can return `404` because Cloud Run file storage is instance-local and does not contain durable historical `data/listing-images`.
- New staging uploads are useful for disposable smoke tests only. They are not durable across rebuilds, revisions, instance changes, or container replacement.

## Target State

- Listing and draft binary images live in Firebase Storage under dealer-scoped paths.
- Marketplace listings and dealer drafts live in Firestore under server-owned collections.
- Dealer isolation remains enforced by server auth context, Firestore rules, Storage rules, and dealer-scoped document/path shape.
- Staging switches to durable backends only after dry-run and limited staging write rehearsal pass:
  - `NONGA_IMAGE_BACKEND=firebase-storage`
  - `NONGA_DATA_BACKEND=firestore`
- Production remains untouched until a separate production migration plan, backup/export plan, rollback rehearsal, and explicit approval.

## File Backend Data Sources

- Marketplace listings: `data/marketplace-inventory.json`
- Dealer drafts: `data/dealer-draft-inventory.json`
- Listing/draft image files: `data/listing-images/{listingIdOrDraftId}/{fileName}`
- Public image references in records: `/storage/listings/{listingIdOrDraftId}/{fileName}`
- Image metadata fields that may appear in draft/listing records:
  - `images`
  - `sourceImageUrls`
  - `imageMetadata`
  - thumbnail fields inside metadata, when present

The repository may not have a committed `data` directory because runtime staging data is local to the Cloud Run instance or ignored local files. The first real dry-run must be run in an environment that can read the intended staging source files.

## Target Firestore Collections

- `dealerListings/{listingId}`
  - Stores marketplace listing records currently represented by `MarketplaceCarRecord`.
  - Must preserve `dealerId`, listing identity, publish status, pricing, vehicle details, duplicate metadata, image URL fields, and owner/showroom fields.
- `dealerDrafts/{draftId}`
  - Stores dealer draft records currently represented by `DealerDraftRecord`.
  - Must preserve `dealerId`, draft status, raw/normalized import data, missing fields, warnings, images, source image URLs, image metadata, duplicate metadata, and timestamps.
- `listingImages/{imageId}` remains a rules-draft metadata projection. The current migration script embeds image metadata into listing/draft documents rather than writing standalone `listingImages` docs.

## Target Firebase Storage Paths

- Published/listing images:
  - `listing-images/{dealerId}/{listingId}/{fileName}`
  - `listing-images/{dealerId}/{listingId}/thumb-{fileName}`
- Draft images:
  - `draft-images/{dealerId}/{draftId}/{fileName}`
  - `draft-images/{dealerId}/{draftId}/thumb-{fileName}`

The path must always include server-trusted `dealerId`. No migration step may derive dealer scope from a raw frontend value or guess from `ownerId`.

## Safe Migration Order

1. Firebase Storage image rehearsal first.
2. Firestore listings/drafts rehearsal second.
3. Switch staging backend flags only after dry-run and limited write rehearsal pass.
4. Keep production untouched.

Rationale: image durability is the current visible blocker for historical images, and Storage path/rules validation can be rehearsed independently before the full data backend switch.

## Dry-Run Plan

Dry-run is report-only and must not write Firestore docs, Storage objects, local source files, deployed config, or backend flags.

1. Confirm repo status is clean and current branch is the staging branch.
2. Confirm staging health still reports:
   - `ok=true`
   - `dataBackend=file`
   - `imageBackend=file`
   - `publicSignupEnabled=false`
3. Confirm no production-like Firebase project env is set.
4. Run static verification first:
   - `npm run test:v50-data-migration`
   - `npm run test:v50-migration-integration`
   - `npm run test:v50-firestore-repository`
   - `npm run test:v50-image-storage-repository`
   - `npm run test:v50-security-rules`
5. Run full dry-run with JSON output:
   - `npm run migrate:v50-file-data -- --dry-run --json`
6. Save/review the report outside the repo if it may contain private listing data.
7. Run limited dry-run for the staging dealer scope:
   - `npm run migrate:v50-file-data -- --dry-run --dealer-id nonga-dealer --limit 5 --json`
   - If source records use another reviewed dealer ID, add a mapping:
     - `npm run migrate:v50-file-data -- --dry-run --dealer-id nonga-dealer --map-dealer-id thor-auto=nonga-dealer --limit 5 --json`
8. Run image-focused dry-run:
   - `npm run migrate:v50-file-data -- --dry-run --dealer-id nonga-dealer --limit 5 --skip-listings --skip-drafts --json`
   - If the script cannot plan images without records, treat that as a tooling gap and use the full/limited dry-run image sections instead.
9. Run data-only dry-run:
   - `npm run migrate:v50-file-data -- --dry-run --dealer-id nonga-dealer --limit 5 --skip-images --json`
10. Review every warning before approving any write rehearsal.

## Dry-Run Checklist

- Count marketplace listings.
- Count dealer drafts.
- Count image folders.
- Count image files.
- Count image files planned for upload.
- Detect missing `dealerId`; records without explicit `dealerId` must skip/warn.
- Detect missing listing or draft `id`; records without IDs must skip/warn.
- Detect existing target docs when existing-state checks are available; do not overwrite by default.
- Detect duplicate planned Storage paths. Current tooling does not expose a dedicated duplicate-path counter; check JSON output for repeated `storagePath` values before write.
- Detect files without matching listing/draft records through the readiness report's `imageFoldersWithoutMatchingRecord`.
- Detect records pointing to missing local image files through the readiness report's `recordsPointingToMissingImageFiles`.
- Detect duplicate planned Storage paths through the readiness report's `duplicateStoragePaths`.
- If source dealer IDs differ from the staging dealer ID, use only a reviewed explicit mapping such as `--map-dealer-id thor-auto=nonga-dealer`.
- Confirm planned listing image paths use `listing-images/{dealerId}/{listingId}/{fileName}`.
- Confirm planned draft image paths use `draft-images/{dealerId}/{draftId}/{fileName}`.
- Confirm no source JSON or local image files changed after dry-run.

## Staging Write Rehearsal Plan

No write rehearsal may run until dry-run output is reviewed and explicitly approved.

1. Use staging project only:
   - `FIREBASE_PROJECT_ID=nonga-ce93c`
   - `FIREBASE_STORAGE_BUCKET` for `nonga-ce93c`
2. Require Admin credentials through one approved source:
   - `FIREBASE_SERVICE_ACCOUNT_JSON`, or
   - `FIREBASE_CLIENT_EMAIL` and `FIREBASE_PRIVATE_KEY`, or
   - `GOOGLE_APPLICATION_CREDENTIALS`
3. Do not print credential values.
4. Require the explicit write gate:
   - `--write --confirm-staging`
5. Block production-like project IDs. Do not use `--allow-production-write` for V5.3 staging rehearsal.
6. Start with data-only tiny subset:
   - `npm run migrate:v50-file-data -- --write --confirm-staging --dealer-id nonga-dealer --map-dealer-id thor-auto=nonga-dealer --limit 1 --skip-images --json`
7. Verify Firestore docs:
   - `dealerListings/{listingId}` or `dealerDrafts/{draftId}` exists only for the selected subset.
   - `dealerId` is preserved and equals the expected staging dealer scope.
   - No unrelated dealer records were written.
8. Re-run the same command without `--overwrite` and confirm existing docs are skipped.
9. Run tiny image-enabled subset:
   - `npm run migrate:v50-file-data -- --write --confirm-staging --dealer-id nonga-dealer --map-dealer-id thor-auto=nonga-dealer --limit 1 --json`
10. Verify Firebase Storage objects:
   - Main image exists under `listing-images/...` or `draft-images/...`.
   - Thumbnail exists under the matching dealer-scoped path.
   - Generated download URL renders the image.
   - Metadata contains `dealerId`, `listingId`, `targetType`, size, width, and height where available.
11. Verify app read behavior while backend flags remain file:
   - Existing app should remain unaffected because staging still reads file backend.
   - Use direct Firestore/Storage inspection or admin-only tooling for migrated subset validation.
12. Only after write rehearsal passes, plan a separate staging backend switch rehearsal with:
   - `NONGA_IMAGE_BACKEND=firebase-storage`
   - then `NONGA_DATA_BACKEND=firestore`
13. Keep rollback to file backend available for every rehearsal step.

## Rollback Plan

Before backend flags switch:

- Keep Cloud Run env unchanged:
  - `NONGA_DATA_BACKEND=file`
  - `NONGA_IMAGE_BACKEND=file`
- Delete or archive only the staging test subset written to Firestore if needed:
  - `dealerListings/{listingId}`
  - `dealerDrafts/{draftId}`
- Delete or archive only the staging test subset written to Firebase Storage:
  - `listing-images/{dealerId}/{listingId}/...`
  - `draft-images/{dealerId}/{draftId}/...`
- Re-run dry-run to confirm source files still exist.

After a staging backend switch rehearsal:

- Roll back Cloud Run env to:
  - `NONGA_DATA_BACKEND=file`
  - `NONGA_IMAGE_BACKEND=file`
- Redeploy only the staging Cloud Run service with the previous known-good env/image if necessary.
- Do not delete file backend source data until a separate production migration has passed.

## Risks

- Cloud Run file backend data may be incomplete or instance-local, so a dry-run from the wrong environment can undercount records/images.
- Historical records may point to image URLs whose local files are absent.
- Records missing explicit `dealerId` cannot be safely migrated without a reviewed mapping.
- Duplicate image filenames can map to the same target Storage path if source data is malformed.
- Firebase Storage download token URLs may need validation for public marketplace rendering.
- Firestore indexes may be required for dealer listing/draft queries at scale.
- Rules drafts must be emulator-tested before any rules deployment.
- Existing route handlers may still call direct file modules in some admin/import paths; repository-backed behavior must be verified before switching data backend broadly.
- `--overwrite` can replace staging test data and must not be used in first rehearsal.
