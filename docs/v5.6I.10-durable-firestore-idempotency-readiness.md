## Risk จาก in-process idempotency

Cloud Run อาจ scale หลาย instance:

```
Instance A                    Instance B
    │                              │
    ├─ POST req-123 (processed)    │
    │  idempotencyCache.set(...)   │
    │                              ├─ POST req-123 (cache miss!)
    │                              │  → duplicate state + audit
```

| ความเสี่ยง | ผล |
|-----------|-----|
| In-process cache ไม่ share ข้าม instance | Double-click / retry อาจสร้าง audit ซ้ำ |
| Transaction เขียน state+audit แต่ไม่มี durable idempotency doc | Race ระหว่าง 2 instance พร้อมกัน |
| Legacy client ไม่ส่ง `requestId` | Server generate `srv-{ts}-{rand}` ใหม่ทุก request → **retry ไม่ idempotent** |
| Backend=firestore แต่ fallback memory เงียบ | ข้อมูลไม่สอดคล้อง — **ห้ามทำ** |

## Deterministic key design

```
idempotencyKey = {listingId}|{updatedBy}|{requestId}
docId          = idem-{listingId}-{safeActor}-{safeRequestId}
```

- Key ไม่ hash — ใช้ composite string สำหรับ lookup ใน transaction
- Doc ID slugify อักขระพิเศษ — ไม่มี `/` (Firestore path safe)
- PII guard: `assertIdempotencyKeyHasNoPii()` — reject phone/email patterns

---

## Payload fingerprint design

```json
{
  "listingId": "...",
  "action": "partial_payment",
  "amount": 500,
  "newFeeAmount": null,
  "reason": "...",
  "adminNote": null,
  "leadId": null
}
```

- `JSON.stringify` ของ normalized fields — **stable** สำหรับ payload เดิม
- Amounts floored to integer
- ไม่รวม `updatedBy` / `requestId` (อยู่ใน key แล้ว)
- Helper: `buildAdjustmentPayloadFingerprint()` (v5.6I.9)

## Transaction flow (future enablement)

```
POST /api/admin/revenue/adjustments
        │
        ▼
  resolveSettlementRequestId()
        │
        ▼
  db.runTransaction(async tx => {
        │
        ├─ READ settlementIdempotencyRecords/{docId}
        │
        ├─ IF NOT EXISTS:
        │     validate payload + audit invariant (pre-tx)
        │     compute next state + audit draft
        │     CREATE idempotency { status: "processing" }
        │     WRITE settlementAdjustments/{stateId}
        │     WRITE settlementAuditLogs/{auditId}
        │     UPDATE idempotency { status: "processed", auditLogId, responseSnapshot }
        │
        ├─ IF EXISTS + same fingerprint:
        │     READ state + audit by auditLogId
        │     RETURN duplicate (no new audit write)
        │
        └─ IF EXISTS + different fingerprint:
              THROW 409 conflict (optionally mark status: "conflict")
  })
        │
        ▼
  IF transaction fail → HTTP 5xx/4xx — ห้ามบอก admin ว่าสำเร็จ
  IF backend=firestore → ห้าม fallback memory เงียบ
```

Steps constant: `DURABLE_IDEMPOTENCY_TRANSACTION_STEPS` in `durableIdempotencyModel.ts`

## Duplicate / replay handling

| กรณี | HTTP | ผล |
|------|------|-----|
| Same key + same fingerprint | 200 | `idempotency.outcome: "duplicate"` — คืน state/audit เดิม |
| Same key + different fingerprint | 409 | `SettlementAdjustmentIdempotencyConflictError` |
| New key | 200 | `idempotency.outcome: "processed"` |

Replay ใช้ `auditLogId` จาก idempotency record — ไม่ append audit ซ้ำ

---

## Conflict handling

- Fingerprint mismatch → reject 409 ทันที
- ไม่ overwrite record ที่ processed แล้ว
- Optional: บันทึก `status: "conflict"` สำหรับ ops audit (future)

## Rules / security plan

`firestore.rules` + `firestore.rules.draft` (repo only — **ยังไม่ deploy ในรอบนี้**):

```
match /settlementIdempotencyRecords/{recordId} {
  allow read, write: if false;
}
match /settlementIdempotencyRecords/{recordId}/{document=**} {
  allow read, write: if false;
}
```

| Role | Direct client access |
|------|---------------------|
| guest / buyer / seller / dealer | **deny** |
| admin / superadmin | **deny** — ต้องผ่าน Cloud Run API |
| Admin SDK (backend) | **allow** (bypasses rules) |

- `responseSnapshot` เก็บเฉพาะ settlement numbers + auditLogId — redact ด้วย `redactIdempotencyResponseSnapshot()`
- Emulator tests: `test:v56i6-settlement-firestore-rules` (extended v5.6I.10)

## Retention / cleanup policy

- **Retention:** 90 วัน (`SETTLEMENT_IDEMPOTENCY_RETENTION_DAYS`)
- `expiresAt = createdAt + 90 days` via `computeIdempotencyExpiresAt()`
- Cleanup: scheduled Cloud Function / cron **เมื่อเปิด persistence จริง** — ลบ docs ที่ `expiresAt < now` และ `status in (processed, conflict, failed)`
- Records `processing` ค้าง > 24h → ops alert + manual review (future)

## Legacy missing requestId risk

| Client | พฤติกรรม | ความเสี่ยง |
|--------|----------|-----------|
| AdminRevenueAdjustmentModal (current) | `useRef` generate once per modal open | Retry หลัง success = duplicate ✓ |
| Legacy / curl ไม่ส่ง requestId | Server `srv-{ts}-{rand}` ใหม่ทุกครั้ง | **Network retry = duplicate adjustment** |
| Double-click ก่อน `submitting` guard | 2 requests อาจมี requestId ต่างกัน (ถ้าไม่มี ref) | Modal มี `submitting` guard แล้ว |

**แนะนำก่อนเปิด writes:** บังคับ client ส่ง `requestId` หรือ deprecate legacy path

## Rollback plan

1. ปิด `NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED` → repo throw ก่อน write
2. สลับ `NONGA_SETTLEMENT_DATA_BACKEND=memory` → runtime กลับ memory (ไม่ fallback เงียบ)
3. Idempotency collection ค้างใน Firestore — ไม่กระทบ memory runtime
4. Rules deny-all ยังป้องกัน client access
