## 3) Listing ownership / recipient binding

### 3.1 How ownership is stored

`MarketplaceCarRecord` (`marketplaceInventory.ts`):

| Field | Role |
|-------|------|
| `ownerId` | **Required** listing owner key. Copied onto lead as `sellerId` at create time. |
| `dealerId` | Optional tent/dealer partition (e.g. `thor-auto`). Used for inventory scope + queue ACL. |
| `ownerName` / `ownerPhone` / `showroomName` | Display / contact metadata (public DTO redacts phone). |

Lead create (`createConsentedBuyerLead`):

```text
sellerId = resolveListingSellerId(listing) = listing.ownerId.trim()
```

- Buyer create body accepts **only** listing + buyer fields + consent — **no** `sellerId` / `dealerId` / recipient override.
- Recipient is **derived only** from the listing’s `ownerId`.

### 3.2 Live staging ownership (redacted)

Marketplace **13** listings observed:

| Group | Count | `dealerId` | `ownerId` (redacted) |
|-------|-------|------------|----------------------|
| Thor Auto imports (`car-import-*`) | **3** | **`thor-auto`** (all three) | **Same** Firebase-style owner id for all three (prefix/suffix only in operator log) |
| Other pilot listings (`v62b-real-pilot-*`) | **10** | Shared non-Thor dealer id | Shared different owner id |

Thor cars observed: MAZDA CX-30, Toyota Camry, Honda CRV — each once; count remains **13**.

**Binding conclusion for Thor:** all three real Thor listings share `dealerId: thor-auto` and the **same** `ownerId`. A lead on any of those listings would set `sellerId` to that listing `ownerId` and be queue-scoped to that listing under the Thor Auto dealer partition.

### 3.3 Unowned / unbound listings

| Case | Behavior |
|------|----------|
| Missing / empty `ownerId` | Create returns **400** — `ไม่พบผู้ขายของประกาศนี้ครับ` |
| Buyer tries to pick another recipient | **Not possible** — no API field; server ignores any extra keys for recipient |
| Listing sold / hidden | Create blocked earlier in route (**400**) |

So unbound (empty owner) listings **cannot** create leads. Listings with a wrong-but-nonempty owner would still create leads to that wrong owner — correctness depends on import/publish setting `ownerId`/`dealerId` correctly (Thor staging rows currently look consistent).

### 3.4 Dealer vs member patterns (code)

| Listing type | Typical `ownerId` | Typical `dealerId` | Lead `sellerId` |
|--------------|-------------------|--------------------|-----------------|
| Dealer tent (canonical create path) | `owner-{dealerId}` e.g. `owner-thor-auto` | `thor-auto` | = `ownerId` |
| Member seller | Firebase `uid` | absent | = member `uid` |
| Thor staging imports (live) | Firebase-style uid (same across 3) | `thor-auto` | = that uid |

Queue **view/manage** for dealers uses `canManageListingWithScope`: match on `dealerId` **or** `ownerId` (or admin). So a Thor Auto dealer account with `dealerId: thor-auto` can manage Thor listings even when `ownerId` is a Firebase uid rather than `owner-thor-auto`.

## 4) Lead queue access control

### 4.1 Who can view a listing’s interest queue

| Actor | Access |
|-------|--------|
| Listing owner (`scope.ownerId === listing.ownerId`) | Yes |
| Dealer whose `dealerId` matches `resolveCarDealerId(listing)` | Yes |
| Admin / superadmin | Yes |
| Other sellers/dealers | **No** — `403` via `canViewSellerQueueForListing` |
| Unauthenticated | **401** on seller queue routes |
| Public | Only `interestCount` via `/api/listings/:id/interest-queue-stats` (no PII) |

Additional guard: `getSellerMaskedQueueForListing` refuses if any lead on that listing has `sellerId` ≠ expected listing owner (`sellerId` from `resolveListingSellerId`).

## 6) Owner-readable summary

### If a buyer submits interest, who receives it?

The **owner of that exact listing**, identified by `listing.ownerId`, stored on the lead as `sellerId`. For Thor Auto’s three staging cars, that is the shared Thor-bound owner id with `dealerId: thor-auto`. The buyer **cannot** choose another dealer or seller.

### Why that person is the correct owner/seller/dealer

Recipient is copied from the listing record at create time, not from buyer input. Thor’s three imports all show `dealerId: thor-auto` and the same owner binding. Queue ACL further restricts view/reveal to that owner, matching dealer id, or admin.

### Can owner/admin review before dealer action?

Admin can open the listing queue. There is **no** mandatory “owner must approve before queue entry” gate. Phone stays locked until someone with listing manage rights **manually reveals**.

### Can other sellers see it?

**No** — other dealers/sellers get **403** on that listing’s queue.

### Listings without owner binding?

Create is **blocked** (400) if `ownerId` is empty.

### Can lead capture be globally turned off?

**Not today.** Design for a default-OFF kill switch is documented above; it is **not** shipped. Until that exists (or equivalent ops control), capture cannot be reliably blocked for authenticated invitees.
