Diagnosis:

1. **Firebase Storage upload succeeded** for the newest 3 duplicates; durable URLs are saved in Firestore and publicly fetchable.

3. Storage permissions / signed URL handling for the newest batch look **correct** (tokenized download URLs return 200).
4. The **original** 3 Thor rows were **not** updated — they still hold ephemeral `/storage/listings/...` paths that 404 on Cloud Run.
5. Owner “no images on newest” is inconsistent with the live durable URLs (possible UI cache / looking at older rows / transient). Regardless, the intended outcome (update originals in place) failed because of duplicate **create**, not because Firebase upload failed on the new rows.
6. Failed-upload overwrite is still a real code risk on other paths (placeholder / empty) — fixed by blank-safe image preserve on upsert.

## 5) Upsert / dedup key and confidence rule

Implemented in `src/server/listingImportIdentity.ts`, wired in `inventoryImportCommit.ts`.

| Precedence | Key | Confidence | Action |
|------------|-----|------------|--------|
| 1 | dealer scope + full plate (+ province when both present) | high (exact, unique) | update existing |
| 2 | dealer scope + VIN exact | high (exact, unique) | update existing |
| 3 | dealer scope + brand/model/year/color/mileage/price fingerprint | high only if **unique** | update existing |
| — | multiple exact hits OR soft brand/model/year overlap without unique key | **ambiguous** | NEED REVIEW — do **not** create |
| — | no match | none | create new |

Rules:

- Masked plate alone (`*`, short tokens) is **not** a sole key.
- Never guess (“มั่วคัน”).
- Opaque `importKey` hash stored on listing; redacted from public DTO.
- Merge: only overwrite fields that are explicitly present/valid; blank/null does not erase good data.
- Images: on failed download/upload, preserve existing working URLs + warning; on success, rewrite onto the **stable** listing id (Firebase Storage when backend is `firebase-storage`).
