## Pilot policy: `hundred_thousand_floor_tier`

คำที่ใช้กับผู้ขาย: **ค่าบริการเมื่อขายสำเร็จ** (ห้ามใช้ “ค่าคอมมิชชั่น” ใน UI ผู้ใช้ทั่วไป)

| ราคาปิดดีล (บาท) | ค่าบริการ |
|------------------|-----------|
| &lt; 100,000 | 500 |
| ≥ 100,000 | `floor(ราคา / 100,000) × 1,000` (ไม่ปัดขึ้น) |

ตัวอย่าง: 80,000→500 · 100,000→1,000 · 250,000→2,000 · 999,000→9,000 · 1,200,000→12,000

**อนาคต:** `percent` (1%) มี helper แต่ **ไม่ใช่ default**

## Settlement data model

`SuccessFeeRecord` (foundation):

- `listingId`, `buyerLeadId`, `sellerId`, `ownerId?`
- `closedDealPrice`, `feeAmount`, `feePolicyType`
- `settlementStatus`: `unbilled` \| `pending_payment` \| `partially_paid` \| `paid` \| `waived` \| `disputed` \| `cancelled`
- `paidAmount`, `remainingAmount` (+ legacy `amountReceived` / `amountDue`)
- `paymentLogs[]` (admin manual log — ไม่มี gateway fields)
- `adminNote?`, `dueAt?`

## Trigger policy (ปิดในรอบนี้)

เมื่อ `closed_won`:

- **ไม่** สร้าง record เรียกเก็บเงินจริง
- **ไม่** เรียก `createSuccessFeeRecordDraft` จาก route
- ถ้าจะทดลองภายหลัง: ตั้ง `NONGA_SUCCESS_FEE_RECORD_ENABLED=true` เท่านั้น (ยังไม่แนะนำบน staging จน review)

## Admin manual workflow (อนาคต)

1. Admin เห็นรายการ `closed_won` / `pending_sale`
2. ตรวจราคาปิดดีลจริง → ตั้ง `closedDealPrice`
3. ระบบคำนวณตาม `hundred_thousand_floor_tier`
4. บันทึกสถานะ: `pending_payment` → `partially_paid` → `paid` / `waived` / `disputed`
5. บันทึกยอดรับจริงใน `paymentLogs` — คง `remainingAmount`
6. ดีลล่ม / ยกเลิก pending sale → `cancelled` หรือ `waived` ตามกรณี

## Seller copy (เตรียมไว้ ยังไม่แสดง)
