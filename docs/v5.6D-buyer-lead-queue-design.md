## แนวคิด

ผู้ซื้อไม่ได้ “ส่งข้อมูลให้ผู้ขาย” แบบกระจาย แต่ **เข้าคิวผู้สนใจรถคันนี้** (`listingId` / `carId`):

| มุมมอง | พฤติกรรม |
|--------|----------|
| **ผู้ซื้อ** | ได้ `queuePosition` ของตัวเองเท่านั้น ไม่เห็นชื่อ/เบอร์คนอื่น |
| **การ์ดรถ / ค้นหา** | อาจเห็นเฉพาะตัวเลขรวม เช่น “มีผู้สนใจเข้าคิวแล้ว X คน” |
| **ผู้ขาย** | เห็นคิวแบบ masked เรียงลำดับ เปิดเบอร์ได้ **ทีละ 1** ตามคิว |
| **หลังเปิดเบอร์** | ต้องบันทึก **outcome** ก่อนเปิดคิวถัดไป |
| **รถ pending_sale / sold** | คิวที่เหลือถูก supersede + แจ้งผู้ซื้อ |

---

## โมเดลข้อมูล (เพิ่มบน `BuyerLead`)

| ฟิลด์ | คำอธิบาย |
|--------|----------|
| `queuePosition` | ลำดับในคิวของ listing นี้ (1-based, ไม่เปลี่ยนหลังสร้าง) |
| `queueLifecycle` | `active` \| `superseded` \| `withdrawn` |
| `contactRevealStatus` | ใช้กฎเดิม v5.6B — `locked` → `revealed` → `outcome_required` |

---

## ข้อจำกัด staging MVP (สำคัญ)

- **In-memory repository** — lead และคิวอยู่ใน RAM ของ process เดียว
- **Restart / redeploy** — ข้อมูล lead/queue **หายทั้งหมด**
- **Multi-instance (Cloud Run หลาย instance)** — คิวอาจ **แยกกัน** ต่อ instance (ลำดับคิวไม่ global)
- **ต้องมี durable persistence (Firestore หรือเทียบเท่า)** ก่อนใช้ production จริง

## API (in-memory staging)

| Method | Path | หมายเหตุ |
|--------|------|----------|
| GET | `/api/listings/:id/interest-queue-stats` | Public — เฉพาะ `interestCount` |
| POST | `/api/buyer-leads` | ตอบ `queuePosition` + ข้อความคิว |
| GET | `/api/seller/listings/:id/buyer-lead-queue` | คิว masked สำหรับเจ้าของประกาศ |
| POST | `/api/seller/buyer-leads/:id/reveal` | เปิดเบอร์คิวที่ถึงลำดับ |
| POST | `/api/seller/buyer-leads/:id/outcome` | บันทึกผล → ปล่อยคิวถัดไป |
| POST | `/api/seller/listings/:id/queue-close` | `pending_sale` / `sold` → supersede คิวที่เหลือ |

## Auth (server)

- Public: `GET .../interest-queue-stats` — ไม่ต้อง login
- Seller: queue / reveal / outcome / queue-close — ต้อง login + `listing.ownerId === uid` (admin bypass บน reveal/outcome)
- ไม่มี dealer role แยกในรอบนี้ — ใช้ `ownerId` ของประกาศเป็นตัวตัดสิทธิ์
