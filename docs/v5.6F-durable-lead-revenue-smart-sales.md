## A) Durable lead persistence

### ปัจจุบัน (ก่อน v5.6F)

| ข้อมูล | ที่เก็บ | หายเมื่อ restart |
|--------|---------|------------------|
| `BuyerLead` + queue fields | `InMemoryBuyerLeadRepository` | ใช่ |
| `LeadContactLog` | array ใน repo เดียวกัน | ใช่ |
| `BuyerPurchaseProfile` | in-memory map (ผ่าน repo v5.6F) | ใช่ |

### แผน Firestore (staging-controlled)

| Collection | Document ID | หลัก fields |
|------------|-------------|-------------|
| `buyerLeads` | `lead.id` | `BuyerLead` ทั้งก้อน |
| `leadContactLogs` | `log.id` | `LeadContactLog` + `buyerLeadId`, `listingId` |
| `buyerPurchaseProfiles` | `buyerUserId` | ไม่มี `contactPhone` |

**Composite indexes (เมื่อเปิด Firestore):**

- `buyerLeads`: `listingId` ASC + `queuePosition` ASC (list queue per listing)  
- `leadContactLogs`: `buyerLeadId` ASC + `createdAt` DESC (audit อนาคต)

### Backend switch

```bash
# default — เหมือนเดิม
NONGA_LEAD_DATA_BACKEND=memory

# staging pilot (Cloud Run + Admin SDK เท่านั้น)
NONGA_LEAD_DATA_BACKEND=firestore
```

- แยกจาก `NONGA_DATA_BACKEND` (listings) — เปิด lead Firestore ได้โดยไม่บังคับเปลี่ยน listings  
- Implementation: `createBuyerLeadRepository()` (server queue/API)  
- `createBuyerPurchaseProfileRepository()` — **server-only**; client ยังใช้ in-memory map ใน `buyerPurchaseProfile.ts` (ไม่ import firebase-admin ใน bundle)  
- **v5.6F ไม่แก้ `firestore.rules`** — server writes ผ่าน Admin SDK; ต้องออก rules ก่อนให้ client อ่าน lead PII โดยตรง

### Security considerations

- Lead PII (`contactPhone`) อยู่ server-only API; อย่า expose collection ให้ client read จนกว่ามี rules + auth claims  
- `buyerPurchaseProfiles` ห้ามเก็บเบอร์ (มี test guard)  
- Logs เป็น audit trail — ยังไม่มี HTTP list API

### Migration จาก in-memory staging

1. เปิด `NONGA_LEAD_DATA_BACKEND=firestore` บน staging หลัง review  
2. **ไม่ migrate production** — ไม่มีสคริปต์ write prod ในรอบนี้  
3. Staging cold start = collection ว่าง; buyer สร้าง lead ใหม่ (ยอมรับได้ช่วง pilot)  
4. Optional ภายหลัง: one-off export/import script จาก RAM snapshot (out of scope v5.6F)

### Local / test strategy

- Tests เรียก `resetBuyerLeadRepositoryForTests()` → บังคับ memory  
- `npm run test:v56f-lead-revenue-foundation` ครอบ factory + policy  
- Firestore integration test แยกรอบ (emulator) หลัง rules draft

## B) Smart Sales Mode

| Tier | พฤติกรรม | v5.6F |
|------|----------|-------|
| `economy` | parser/template ก่อน | **default** |
| `smart_sales` | AI text เฉพาะจุด (parse ต่ำ, สรุปคุณภาพ, ต่อรอง, แนะนำรถ) | hooks มี, **API ยัง null** |
| `premium_sales_future` | แพ็กเกจ dealer / รายได้จริง | เอกสารเท่านั้น |

### Feature flags (env — ยังไม่แก้ `.env` ในรอบนี้)

| Flag | Default | ความหมาย |
|------|---------|----------|
| `BUYER_LEAD_AI_TEXT_PARSE_ENABLED` | `false` | อนุญาต AI parse fallback |
| `NONGA_SMART_SALES_MODE` | `economy` | ต้องเป็น `smart_sales` + flag ด้านบนจึงเรียก AI hooks |

### Guards (`smartSalesAiGuards.ts`)

- max input 2000 chars  
- ห้ามขอเอกสารสำคัญ / ภาษาค่าคอม / สัญญาอนุมัติไฟแนนซ์หรือการันตีขาย  
- structured output ห้ามฟิลด์ VIN/เบอร์/ทะเบียน

### AI/API สถานะ v5.6F

**ปิดทั้งหมด** — `trySmartSalesAiBuyerLeadParse`, `trySmartSalesLeadQualityNarrative`, `trySmartSalesNegotiationHint` คืน `null` เสมอจนกว่าจะ wire Gemini ในรอบถัดไป

## C) Lead quality score

Module: `src/services/leads/leadQualityScore.ts`

| Tier | ช่วง score (โดยประมาณ) |
|------|-------------------------|
| `hot` | ≥ 75 |
| `warm` | 55–74 |
| `needs_info` | 35–54 |
| `risky` | < 35 |

ปัจจัย: ความครบข้อมูล, วิธีซื้อ vs seller criteria, ราคาเสนอ vs floor (10% ใต้ประกาศ หรือ `minimumAcceptablePrice`), ช่วงติดต่อ, ภาษาน่าสงสัย, รายงาน suspicious (**ไม่ลงโทษอัตโนมัติ** — ใช้ `applySuspiciousBuyerReportPolicy`)

## Risks ที่เหลือ

- เปิด `NONGA_LEAD_DATA_BACKEND=firestore` บน staging โดยไม่มี rules → client ยังไม่ควรอ่าน collection โดยตรง

- Lead quality ยังไม่แสดงใน seller UI — ต้อง wire หลัง review
