# V5.3C Clean Firestore/Storage Staging Rehearsal Plan

Date recorded: Tuesday May 26, 2026

This runbook replaces the earlier "migrate old file backend data" direction for V5.3. The new direction is to keep old noisy/test file data out of Firestore and Firebase Storage, switch staging to clean durable backends only after readiness fixes, and create fresh test data through the real web UI.

This document does not include secrets, passwords, tokens, API keys, service account JSON, or private user identifiers.

## Decision

Do not migrate old file-backend data into Firestore or Firebase Storage.

Reasons:

- The current file backend contains a large amount of staging/test/noisy data.
- Prior dry-run found missing dealer IDs, missing local image files, and many orphan image folders.
- Importing old noisy data would make Firestore/Storage harder to validate and clean up.
- The better staging rehearsal is a clean durable backend with new data created through actual user flows.

The V5.3B migration mapping/reporting tooling remains useful for audits, exports, and future cleanup, but it is not the next path for staging write rehearsal.

### Ready

- Repository layer exists:

  - `src/server/listingImageUploadBody.ts`
- Existing repository tests cover the Firestore/Storage-ready layers:
  - `npm run test:v50-firestore-repository`
  - `npm run test:v50-image-storage-repository`

### Not Yet Ready For Switch

Several core API paths still call file-backed modules directly instead of the inventory repository:

- `src/server/dealerPortalRoutes.ts`
  - Draft create/list/update/delete still uses `dealerDraftInventory`.
  - Dealer inventory list/edit/delete still uses `marketplaceInventory`.
  - Draft publish calls `publishDealerDraftToMarketplace()`, which is currently file-backed.
  - Dealer import commit calls `processSmartInventoryImport()`, which is currently file-backed.
- `src/server/publishDraftListing.ts`
  - Reads draft from file backend.
  - Copies local image files with `migrateListingImagesToCarId()`.
  - Writes published listing through `addMarketplaceCar()`.
  - Deletes draft through `removeDealerDraft()`.
- `src/server/ownerListingRoutes.ts`
  - Owner listing edit/visibility/delete still uses `marketplaceInventory`.
- `src/server/ownerListingAccess.ts`
  - Owner listing scope lookup still uses file-backed marketplace access helpers.
- `src/server/inventoryImportCommit.ts`
  - Bulk/import commit still uses file-backed marketplace/draft modules.
  - Remote image download still uses local file image helpers.
- `server.ts`
  - `GET /api/cars` and `POST /api/cars` still use file-backed marketplace functions.
  - `/storage/listings` still serves local file images.

Conclusion: image uploads are closer to Firebase Storage readiness than listing/draft data routes. A clean switch should not be deployed until the core dealer listing/draft/publish routes are wired through the repository layer or explicitly tested behind a narrow staging-only route path.

## Safe Staging-Only Switch Plan

Phase 0: no write, no deploy

1. Keep staging on file/file.
2. Confirm health:
   - `ok=true`
   - `dataBackend=file`
   - `imageBackend=file`
   - `publicSignupEnabled=false`
3. Confirm GitHub branch is pushed and working tree is clean.
4. Confirm Firestore and Storage rules are ready for emulator/staging validation.

Phase 1: code readiness fix, still no deploy

1. Route dealer draft/listing operations through `createInventoryRepository()`.
2. Route draft publish through `InventoryRepository.publishDraft()` or an equivalent repository-backed service.
3. Ensure publish from draft does not call local `migrateListingImagesToCarId()` when Storage is active.
4. Route owner listing edit/visibility/delete through the repository layer or document that owner listing is blocked for this rehearsal.
5. Decide whether admin import/bulk import is included. If included, route it through repositories; if not, mark it out of scope for V5.3C.
6. Add focused tests for Firestore-backed draft create/list/update/publish and image upload behavior.

Phase 2: staging deploy only after approval

1. Deploy Cloud Run staging only with:
   - `NONGA_DATA_BACKEND=firestore`
   - `NONGA_IMAGE_BACKEND=firebase-storage`
   - public signup still false
2. Do not deploy production.
3. Do not run migration.
4. Do not import old file data.

Phase 3: create fresh data through UI

1. Login as the staging dealer.
2. Create a new draft from Dealer create listing.
3. Upload at least one new image.
4. Save draft.
5. Publish listing.
6. Edit listing fields.
7. Upload/replace image after publish if supported.
8. View listing in Marketplace.
9. Confirm member/admin/superadmin role boundaries still hold.

Phase 4: durability verification

1. Record the created staging listing/draft IDs and Storage URLs in a private test note, not in committed docs if they contain private data.
2. Redeploy/restart Cloud Run staging with the same firestore/firebase-storage flags.
3. Confirm the listing still appears in Dealer Portal and Marketplace.
4. Confirm images still render from Firebase Storage URLs.
5. Confirm `/api/health` reports:
   - `dataBackend=firestore`
   - `imageBackend=firebase-storage`
   - `publicSignupEnabled=false`
