## 1) Code audit findings

### Routes → repositories

| Route | Repository | หมายเหตุ |
|-------|------------|----------|
| `GET /api/admin/revenue/preview` | `createSettlementAdjustmentRepository()` | อ่าน overlay; derive rows จาก inventory |
| `POST /api/admin/revenue/adjustments` | เดียวกัน | `upsertState` + `appendAudit` ต่อเนื่อง |
| `GET /api/my/revenue/preview` | เดียวกัน | seller scope + overlay |

**ไฟล์:** `src/server/revenuePreviewRoutes.ts` — inject ได้ผ่าน `RevenuePreviewRoutesDeps.settlementAdjustmentRepository`

**ไม่ได้ใช้:** `createSuccessFeeRecordRepository()` ใน routes — success fee records **ยังไม่ wire** ไป API/runtime

### Firestore repo wiring

Factory pattern ใน:

- `createSettlementAdjustmentRepository()` → `memory` (default) หรือ `createFirestoreSettlementAdjustmentRepository()` เมื่อ `NONGA_SETTLEMENT_DATA_BACKEND=firestore`
- `createSuccessFeeRecordRepository()` → เดียวกัน

Firestore impl มีอยู่ (`*RepositoryFirestore.ts`) แต่ **staging ยังไม่เลือก** เพราะ backend default = `memory`

### Flag gates

| Function | เงื่อนไข |
|----------|----------|
| `resolveSettlementDataBackend()` | `memory` unless env = `firestore` |
| `isSettlementFirestoreWritesEnabled()` | env === `"true"` |
| `isSuccessFeeRecordEnabled()` | env === `"true"` |
| `isDurableSettlementPersistenceActive()` | **ทั้ง 3 ต้อง true** |

**Write gate จริงใน Firestore repo:** `assertWritesAllowed()` ตรวจเฉพาะ `NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED` — แต่ durable active ต้องครบ triple gate สำหรับ auto-create closed_won

### Success fee record creation

| Path | พฤติกรรมตอนนี้ |
|------|----------------|
| `createSuccessFeeRecordDraft()` | return **`null`** เมื่อ flag off |
| `createSuccessFeeRecordDraftPreview()` | เปิด flag ชั่วคราว — **tests/admin tools เท่านั้น** |
| `shouldAutoCreateSuccessFeeOnClosedWon()` | **false** — ไม่ wire closed_won routes |
| Admin revenue derive | `buildDerivedRevenuePreviewRowFromListing()` — **ไม่ persist** |

### ถ้าเปิด flag อย่างเดียว (what-if)

| การเปิด | ผลที่คาด |
|---------|----------|
| `NONGA_SETTLEMENT_DATA_BACKEND=firestore` เท่านั้น | Factory เลือก Firestore repo; **reads** จาก collection ว่าง; preview ยัง derive จาก inventory; POST adjustment **ล้ม** ถ้า writes off; overlay หายจาก memory แต่ไม่มีใน Firestore |
| `NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED=true` + memory backend | Memory repo ยังใช้อยู่ — writes flag **ไม่มีผล** จนกว่า backend=firestore |
| Writes on + firestore backend, success fee **off** | Adjustment/audit **เขียน Firestore ได้** (Admin SDK bypass rules); success fee auto-create ยัง **ไม่เกิด**; ไม่ durable active ตาม `isDurableSettlementPersistenceActive` |
| ครบ triple gate | พร้อมสำหรับ durable writes + auto-create closed_won (เมื่อ wire routes ในอนาคต) |

### จุดเสี่ยงข้อมูลเงินหาย/ซ้ำ/ไม่ตรง

| ความเสี่ยง | สาเหตุ | แผนลด |
|-----------|--------|-------|
| Overlay หายหลัง Cloud Run restart | in-memory only | Phase 3+ Firestore writes |
| State มีแต่ไม่มี audit | route เรียกแยก 2 ครั้ง ไม่มี transaction | Phase 3: batch/transaction หรือ fail-closed rollback |
| Audit ซ้ำจาก double-submit | audit id = `adj-audit-${Date.now()}-random` | Idempotency-Key / `requestId` (§5) |
| Success fee ซ้ำต่อ listing | ยังไม่มี unique constraint | deterministic `sfr-{listingId}` + upsert merge |
| Preview ไม่ตรง durable | derive vs overlay คนละ source | Phase 2 compare; Phase 5 backfill align |
| Admin คิดว่าบันทึกสำเร็จแต่ Firestore fail | ไม่มี fail-closed วันนี้ | §4 — return 5xx, ไม่ fallback silent |

## 2) Flag matrix

| Flag | Default | Phase ที่เปิด | ผล |
|------|---------|---------------|-----|
| `NONGA_SETTLEMENT_DATA_BACKEND` | `memory` | Phase 1+ staging | เลือก repo implementation |
| `NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED` | off | Phase 3+ staging | อนุญาต Admin SDK writes |
| `NONGA_SUCCESS_FEE_RECORD_ENABLED` | off | Phase 4+ staging | auto-create draft + persist fee records |

**Triple gate (`isDurableSettlementPersistenceActive`):** ต้องครบทั้ง 3 ก่อนถือว่า "durable settlement persistence เปิดจริง" สำหรับ closed_won auto-create

**Kill-switch (rollback เร็ว):**

```text
NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED=false  → หยุด write ทันที
NONGA_SETTLEMENT_DATA_BACKEND=memory             → กลับ in-process overlay
NONGA_SUCCESS_FEE_RECORD_ENABLED=false           → หยุด auto-create
```

## 4) Write / read behavior plan

| หลักการ | นโยบาย |
|---------|--------|
| Memory default | `NONGA_SETTLEMENT_DATA_BACKEND` default `memory` — fallback ปลอดภัย |
| Explicit write flag | Firestore `upsert`/`appendAudit` ต้องผ่าน `NONGA_SETTLEMENT_FIRESTORE_WRITES_ENABLED=true` |
| Fail closed on durable write failure | **ต้อง implement ก่อน Phase 3:** ถ้า Firestore write ล้ม → HTTP 5xx/4xx ชัดเจน — **ห้าม** return success |
| No silent fallback to memory after Firestore selected | ถ้า backend=firestore แล้ว write fail — **ไม่** fallback เขียน memory โดยไม่แจ้ง admin |
| Reads | Firestore reads อนุญาตเมื่อ backend=firestore (Admin SDK bypass client rules) |
| Client Firestore | **ไม่ต้องการ** — revenue ใช้ REST API เท่านั้น |
| Payment / invoice | ยังไม่มี — manual adjustment warning คงเดิม |

### Adjustment + audit invariant

ทุก `POST /api/admin/revenue/adjustments` ต้อง:

1. `applySettlementAdjustment()` → `{ next, audit }`
2. `upsertState(next)` สำเร็จ
3. `appendAudit(audit)` สำเร็จ — **ถ้าขั้น 3 ล้ม ต้องไม่ถือว่าสำเร็จ** (future: transaction)

ห้าม:

- adjustment state โดยไม่มี audit event
- audit โดยไม่มี `reason` หรือ before/after ที่ไม่เปลี่ยน (ยกเว้น `note_added`)
- บันทึก buyer phone/contact ใน settlement docs

## 5) Idempotency plan

| Entity | Proposed deterministic id | กัน duplicate |
|--------|---------------------------|---------------|
| Settlement state doc | `settlementId` = `preview-pending-{listingId}` (มีอยู่แล้วใน `syntheticSettlementId`) | `doc(settlementId).set(merge:true)` |
| Success fee record | `sfr-{listingId}` | upsert by listingId query + same doc id |
| Audit log | `adj-audit-{listingId}-{requestId}` | `requestId` จาก client header หรือ body; reject duplicate |
| Backfill batch | `backfill-{listingId}-{batchRunId}` | dry-run รายงาน would-create vs skip |

**Double-submit:** Phase 3+ ควรรับ `requestId` (optional) ใน POST body — ถ้าซ้ำ return prior result แทนสร้าง audit ใหม่

**Correlation:** `correlationId` / `requestId` fields ใน durable model พร้อมแล้ว (`settlementPersistenceModel.ts`)

## 6) Backfill readiness plan (ยังไม่รัน)

### Source

- Inventory listings ที่ `saleStatus === "pending_sale"`
- ไม่สร้างจาก published-only listings

### Deterministic record id

```text
recordId = `sfr-${listingId}`
settlementId = `preview-pending-${listingId}`  (มีอยู่แล้ว)
```

### Duplicate prevention

1. Dry-run: list existing `successFeeRecords` where `listingId == X`
2. Skip ถ้ามี doc แล้ว
3. Upsert merge ไม่ overwrite `paidAmount` ถ้ามี adjustment overlay ใหม่กว่า

### Field mapping

| Field | Source |
|-------|--------|
| `listingId` | car.id |
| `sellerId` | ownerId \|\| dealerId |
| `ownerId` / `dealerId` | จาก listing |
| `leadId` | optional — จาก deal outcome ถ้ามี; **ถ้าไม่มี → omit** |
| `closedDealPrice` | listing.closedDealPrice \|\| listing.price |
| `feeAmount` | `calculateSuccessFeeByClosedPrice(closedDealPrice)` |
| `feePolicyType` | `DEFAULT_SUCCESS_FEE_POLICY` |

### Dry-run output ต้องมี

- `listingId`, `recordId`, `sellerId`, `feeAmount`, `closedDealPrice`
- `action`: create | skip-exists | skip-invalid-price
- `errors[]` สำหรับ row ที่คำนวณไม่ได้
- **ไม่มี** buyer phone/PII ใน log

### Rollback / backout

- Mark records `settlementStatus: cancelled` + `cancelledReason: backfill-rollback-{runId}`
- หรือลบ docs ที่สร้างใน batch เดียว (เก็บ `batchRunId` ใน `correlationId`)
- ไม่ลบ adjustment/audit ที่ admin สร้าง manual

### Validation หลัง backfill

- Count `pending_sale` listings ≈ count fee records (± skipped)
- Sample 10 rows: feeAmount ตรง derive preview
- Admin revenue preview ยังไม่แสดง PII
- Seller scope ไม่เห็นรายการคนอื่น
