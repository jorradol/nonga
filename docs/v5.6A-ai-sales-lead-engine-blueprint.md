## 1. Vision

### Nong A คืออะไรใน v5.6

Nong A **ไม่ใช่แค่ marketplace** แต่เป็น **AI Sales Assistant สำหรับรถมือสอง** ที่ทำงานคู่กับตลาดรถและแชทที่มีอยู่แล้ว:

| บทบาท | สิ่งที่น้องเอช่วย |
|--------|-------------------|
| **ผู้ซื้อ** | ค้นหารถ, เปรียบเทียบ, ต่อรองในกรอบที่ผู้ขายกำหนด, ตัดสินใจ — พร้อมสรุปความต้องการให้ผู้ขายเมื่อผู้ซื้อยินยอม |
| **ผู้ขาย** | คัดกรองผู้ซื้อจริง, รับลีดที่มีบริบท (งบ, วิธีซื้อ, ข้อเสนอราคา, ความพร้อม) แทนการได้เบอร์ดิบทันที |
| **แพลตฟอร์ม** | สร้างรายได้จาก **ค่าบริการเมื่อขายสำเร็จ** (success fee) — ไม่คิดเงินจากการที่น้องเอ “ขายไม่ได้” |

### หลักการสำคัญ

- **รักษาระบบเดิมทั้งหมด** — flow marketplace, chat, dealer showroom, member listing, auth, duplicate detection, image storage ยังทำงานเหมือนเดิม
- **Lead engine เป็นเลเยอร์เสริม** — ไม่แทนที่การค้นหา/ดูรถ/แชทปัจจุบัน แต่เพิ่ม consent-based lead handoff และ seller inbox
- **น้องเอไม่รับประกันการปิดการขาย** — ช่วยจับคู่และสรุปข้อมูล ผู้ขายและผู้ซื้อตัดสินใจและทำสัญญานอกแพลตฟอร์มตามเดิม
- **รอบ blueprint นี้** — เอกสารเท่านั้น ไม่มี API, UI, Firestore, payment, หรือ Gemini call จริง

### ความสัมพันธ์กับของเดิม

```
[ผู้ซื้อ] ──แชทน้องเอ──► [ค้นหา/การ์ดรถ marketplace] (เดิม)
                │
                └──► [Buyer Lead + Consent] (ใหม่ — v5.6C+)
                          │
                          ▼
                [Seller Masked Inbox] (ใหม่ — v5.6D+)
                          │
                          └──► [Contact Reveal + Outcome] (ใหม่ — v5.6E+)
```

Analytics `Lead` / `AiLeadScore` ในโค้ดปัจจุบันเป็น sandbox/ต้นแบบ — **Lead Engine ในเอกสารนี้** หมายถึง lead ที่มี consent, masked contact, และ outcome ที่ผูกกับ listing — จะออกแบบ collection/ชื่อใหม่ใน v5.6B เพื่อไม่ชน type เดิมโดยไม่ตั้งใจ

## 2. Buyer Lead Flow

### ลำดับเหตุการณ์ (เป้าหมาย)

1. ผู้ซื้อคุยกับน้องเอในแชทหลัก (flow เดิม)
2. เมื่อสนใจรถคันใด น้องเอถามข้อมูลเบื้องต้น **ทีละขั้น ไม่ถามยัดเยียด**
3. ก่อนส่งข้อมูลให้ผู้ขาย ต้องได้ **consent ชัดเจน** จากผู้ซื้อ
4. หลัง consent ระบบสร้าง lead snapshot และส่งเข้า seller inbox (masked)

### ข้อมูลที่น้องเอถาม (รอบแรก)

| ฟิลด์ | คำถามตัวอย่าง (โทนอบอุ่น) |
|--------|---------------------------|
| งบประมาณ | “งบประมาณคร่าว ๆ อยู่ช่วงไหนครับ?” |
| วิธีซื้อ | “ซื้อสด ไฟแนนซ์ หรือยังไม่แน่ใจครับ?” |
| ราคาที่เสนอ | “ถ้าสนใจคันนี้ ราคาที่อยากเสนอประมาณเท่าไหร่ครับ?” |
| เวลาติดต่อ | “ช่วงไหนสะดวกให้ผู้ขายติดต่อกลับครับ?” |
| ชื่อ/ชื่อเล่น, เบอร์ | ถามเมื่อใกล้ส่ง lead — **พร้อม consent** |

### Consent (บังคับ)

- แสดงข้อความสรุปว่าจะส่งอะไรให้ผู้ขายบ้าง (ไม่รวมเอกสารสำคัญ)
- ปุ่มยินยอมชัดเจน เช่น “ยินยอมให้ส่งข้อมูลนี้ให้ผู้ขายติดต่อกลับ”
- บันทึก `consentedAt`, `consentVersion`, `listingId` ที่เกี่ยวข้อง
- **ห้าม** ส่งเบอร์หรือชื่อจริงให้ผู้ขายก่อน consent
- **ห้าม** ส่งข้อมูลส่วนตัวให้ผู้ขายโดยผู้ซื้อไม่ยินยอม (PDPA)

### สิ่งที่น้องเอต้องไม่ทำ

- รับประกันว่าผู้ซื้อจริง 100%
- รับปากราคาแทนผู้ขาย (ดู [Negotiation Guard](#9-negotiation-guard))
- ขอเอกสารสำคัญใน flow แรก

## 3. Lead Data — รอบแรก

### ฟิลด์ที่เก็บได้

| ฟิลด์ | ประเภท | หมายเหตุ |
|--------|--------|----------|
| `displayName` | string | ชื่อหรือชื่อเล่น |
| `contactPhone` | string | เบอร์ติดต่อ — **masked จนกว่า seller reveal** |
| `listingId` / `carId` | ref | รถที่สนใจ |
| `budgetMin` / `budgetMax` | number? | งบประมาณ (ช่วงหรือค่าเดียว) |
| `purchaseMethod` | enum | `cash` \| `finance` \| `undecided` |
| `offeredPrice` | number? | ราคาที่ผู้ซื้อเสนอ |
| `preferredContactWindow` | string | เวลาที่สะดวกให้ติดต่อ |
| `buyerSummary` | string | สรุปความต้องการจากน้องเอ (snapshot) |
| `consent` | object | เวอร์ชัน + timestamp |
| `source` | enum | `chat` (รอบแรก) |
| `status` | enum | เริ่มที่ `pending_seller` หลัง consent |

### ห้ามเก็บใน flow แรก

- บัตรประชาชน, เล่มทะเบียน, สลิปเงินเดือน
- เลขบัญชี, สัญญาไฟแนนซ์, เอกสาร KYC เต็มรูปแบบ

ถ้าผู้ใช้ส่งเอกสารในแชท — น้องเอเตือนอย่าเก็บ/อย่าส่งต่อ และไม่ใส่ใน lead snapshot

### Lead snapshot

- สร้างครั้งเดียวตอน consent เพื่อลด drift และต้นทุน AI
- อัปเดตเฉพาะเมื่อผู้ซื้อยืนยันการเปลี่ยน (รอบถัดไป)

## 4. Seller Lead Inbox

### ประสบการณ์ผู้ขาย

ผู้ขาย (dealer หรือ member owner) เห็น **ลีดที่คัดกรองแล้ว** ใน inbox แยกตามรถหรือรวมทั้งหมด (รายละเอียด UI ใน v5.6D):

| เห็นทันที | ยังไม่เห็นจนกว่ากด reveal |
|-----------|---------------------------|
| สนใจรถคันไหน (title, ราคาประกาศ) | เบอร์โทร |
| งบประมาณ | ชื่อเต็ม (ถ้าแยกจากชื่อเล่น) |
| วิธีซื้อ | |
| ข้อเสนอราคา | |
| ความพร้อมติดต่อ | |
| สรุปความต้องการจากน้องเอ | |
| เวลาที่สร้าง lead | |

### การดำเนินการ

1. อ่านสรุปลีด
2. กด **“ต้องการติดต่อผู้ซื้อรายนี้”**
3. ระบบบันทึก `contactRevealedAt` และแสดงเบอร์ (และชื่อตามนโยบาย)
4. สถานะ lead เปลี่ยนเป็น `contacting` (หรือเทียบเท่าใน [Contact Reveal](#5-contact-reveal-rule))

### ไม่ทำลาย flow เดิม

- การแชทสาธารณะ, การดู analytics เดิม, การแก้ประกาศ — ยังใช้ได้
- Inbox ใหม่เป็น **ทางเสริม** สำหรับลีดที่มี consent ไม่บังคับยกเลิกช่องทางติดต่อนอกระบบที่ผู้ใช้ทำอยู่แล้ว (แต่แพลตฟอร์มแนะนำใช้ inbox เพื่อ success fee และ audit trail)

## 5. Contact Reveal Rule

### กฎต่อรถ 1 คัน

สำหรับ listing เดียวกัน ผู้ขายควร **เปิดเบอร์ผู้ซื้อได้ทีละราย** (active reveal):

```
Lead A ── reveal ──► ต้องอัปเดต outcome ก่อน
                              │
                              ▼
Lead B ── reveal ได้
```

- หลังเปิดเบอร์แล้ว ต้องเลือก/อัปเดต **ผลการติดต่อ** ก่อนจึงจะเปิดเบอร์ลีดถัดไปได้ (ยกเว้น admin override ในอนาคต)
- ป้องกันการดึงเบอร์จำนวนมากโดยไม่ติดตามผล

### สถานะผลการติดต่อ (seller-facing)

| ค่าในระบบ | ข้อความ UI (แนะนำ) |
|-----------|---------------------|
| `contacting` | กำลังติดต่อ |
| `viewing_scheduled` | นัดดูรถแล้ว |
| `unreachable` | ติดต่อไม่ได้ |
| `no_progress` | **ไม่ได้ไปต่อ** (ใช้คำนี้แทน “ไม่จบ” — สุภาพกว่า) |
| `not_closed` | ไม่ปิดการขาย |
| `closed_won` | ปิดการขายแล้ว |
| `reported_to_admin` | รายงานให้แอดมินตรวจสอบ |

### เหตุการณ์ระบบ

- `closed_won` → เริ่ม [Deal Outcome Flow](#6-deal-outcome-flow)
- `reported_to_admin` → เข้า moderation (อาจค้าง reveal ลีดถัดไปจน admin ปิดเคส)
- `unreachable` / `no_progress` → ปลดล็อก reveal ลีดถัดไปได้หลังบันทึก

## 6. Deal Outcome Flow

### เมื่อปิดการขาย (`closed_won`)

1. ผู้ขายยืนยันปิดการขาย + ราคาปิดจริง (สำหรับ success fee ในอนาคต)
2. รถเปลี่ยนสถานะเป็น **`pending_sale`** หรือ **`sold`** ตามนโยบาย:
   - `pending_sale` — กำลังดำเนินการโอน/ชำระ (default หลังปิดการขาย)
   - `sold` — ยืนยันขายออกแล้วสมบูรณ์

### การซ่อนจาก marketplace

- เมื่อเข้าสู่ **`pending_sale`** รถต้อง **หายจาก public marketplace ทันที** (ไม่แสดงในผลค้นหา/การ์ด/ลิงก์สาธารณะ)
- Car detail สาธารณะแสดงข้อความเหมาะสม เช่น “รถคันนี้อยู่ระหว่างดำเนินการขาย”
- ป้องกันผู้ซื้อคนอื่นสับสนหรือต่อรองซ้ำ

### ถ้าดีลล่ม

- เปลี่ยนสถานะ lead กลับเป็น `not_closed` หรือ `no_progress`
- คืน listing เป็น **`published`** (หรือสถานะเดิมก่อน pending) เพื่อขายต่อได้
- ไม่สร้าง success fee หรือยกเลิกรายการค้างชำระถ้ายังไม่ยืนยัน

### แจ้งเตือน 7 วัน (`pending_sale`)

- หลัง `pending_sale` ครบ **7 วัน** ระบบเตือนผู้ขาย:
  - อัปเดตผลเป็น `sold` หรือยกเลิก pending
  - แจ้งยอดปิดการขาย / ค่าบริการเมื่อขายสำเร็จ (เมื่อเปิด billing ใน v5.6G)
- รอบ blueprint: บันทึกกฎในเอกสารเท่านั้น — cron/notification ใน v5.6F+

### การผูกกับ listing status ปัจจุบัน

โค้ดปัจจุบันใช้ `listingStatus` เช่น `published` / `hidden` — ใน v5.6B จะเสนอเพิ่ม `pending_sale` | `sold` โดยไม่ทำลายค่าเดิม และ map กับ duplicate/hidden logic ที่มีอยู่

## 7. Notify Other Interested Buyers

### เมื่อไหร่แจ้ง

เมื่อ listing ของรถคันนั้นเข้า **`pending_sale`** หรือ **`sold`**:

- ค้นหาผู้ซื้อที่เคยสนใจรถคันเดียวกัน (lead ที่ยังไม่ปิด, favorite, chat inquiry ที่บันทึกไว้ — นิยามใน v5.6B)
- ส่งข้อความในแชทน้องเอ (หรือ in-app notice) **ทีละคน ไม่ spam**

### โทนข้อความ (ตัวอย่าง)

> รถคันที่คุณสนใจมีผู้ซื้อดำเนินการแล้ว/ขายออกแล้วครับ  
> น้องเอช่วยแนะนำรถใกล้เคียงให้แทนได้ — บอกงบหรือรุ่นที่อยากได้ต่อได้เลยครับ

### หลักการ

- สุภาพ ไม่เปิดเผยข้อมูลผู้ซื้อรายที่ปิดการขาย
- เสนอทางเลือก (deterministic search / scored marketplace ที่มีอยู่) แทนการจบบทสนทนา
- ไม่เรียก Gemini เพิ่มในรอบแรก — ใช้เทมเพลต + search ที่มี

## 8. Scam / Suspicious Buyer Report

### ผู้ขายรายงานได้เมื่อ

- เบอร์ปลอม / ติดต่อไม่ได้หลัง reveal
- พฤติกรรมสงสัยมิจฉาชีพ (ขอโอนก่อนดูรถ, บัตรปลอม ฯลฯ — อธิบายเป็นข้อความ)

### Flow

1. ปุ่ม “รายงานให้แอดมินตรวจสอบ” ใน lead detail
2. สร้างรายการใน **admin moderation queue** (คล้าย `CarReport` แต่ประเภท buyer-lead)
3. **ห้ามลงโทษอัตโนมัติ** — admin ตรวจสอบก่อน (suspend, แบน, ลด trust score)
4. Lead สถานะ `reported_to_admin` — เก็บ audit log

### สิ่งที่ admin เห็น

- สรุป lead, ประวัติ reveal, ข้อความรายงาน, เบอร์ (จำกัดสิทธิ์)
- การตัดสินใจ: ปิดเคส / เตือนผู้ซื้อ / ระงับบัญชี (manual)

## 9. Negotiation Guard

### ข้อมูลราคาที่ผู้ขายตั้ง

| ฟิลด์ | คำอธิบาย |
|--------|-----------|
| `listedPrice` | ราคาประกาศ (มีอยู่แล้ว) |
| `minimumAcceptablePrice` | ราคาต่ำสุดที่รับได้ (optional) |

### Default floor

ถ้าไม่ตั้ง `minimumAcceptablePrice`:

```
floor = listedPrice × 0.90   // ต่ำกว่าราคาประกาศ 10%
```

(ค่า 10% เป็นค่าเริ่มต้นใน blueprint — ปรับได้ใน config รอบ implement)

### พฤติกรรมน้องเอ

- **ห้ามรับปากแทนผู้ขาย** — ไม่พูดว่า “ราคานี้ได้แน่นอน”
- ถ้าผู้ซื้อเสนอต่ำกว่า floor:
  - อธิบายว่าราคาที่เสนอต่ำกว่าที่ผู้ขายเปิดรับ
  - **เสนอรถคันอื่น** ที่สเปกใกล้เคียงแต่ราคาต่ำกว่า (ใช้ deterministic / scored search ที่มี)
- ถ้าใกล้ floor — ชวนผู้ซื้อปรับข้อเสนอหรือส่ง lead ให้ผู้ขายพิจารณา (ไม่สัญญาแทน)

### บันทึกใน lead

- `offeredPrice` เทียบกับ `floorAtCapture` เพื่อ analytics และ seller inbox

## 10. Success Fee Model

### ขอบเขตรอบนี้

- **ยังไม่เปิด payment จริง** — ไม่มี gateway, ไม่มี webhook, ไม่เก็บบัตร
- ออกแบบโมเดลและคำศัพท์ user-facing สำหรับ pilot ถัดไป

### คำศัพท์ user-facing

ใช้ **“ค่าบริการเมื่อขายสำเร็จ”** แทน “คอมมิชชั่น” / “ค่าธรรมเนียมแพลตฟอร์ม” ในหน้าผู้ขาย

### Model A — เปอร์เซ็นต์

| รายการ | ค่า |
|--------|-----|
| อัตรา | **1%** ของราคาปิดการขายจริง |
| ข้อดี | สมดุลกับราคารถ |
| ข้อเสีย | ผู้ขายอาจคำนวณยาก, รถราคาสูงได้ยอดมาก |

### Model B — เรทราคา (แนะนำ pilot)

คิดจาก **ราคาปิดการขายจริง** (หรือราคาประกาศถ้ายังไม่มีปิด — กำหนดใน v5.6G):

| ช่วงราคาปิด (บาท) | ค่าบริการเมื่อขายสำเร็จ |
|-------------------|-------------------------|
| ไม่เกิน 100,000 | 500 |
| 100,001 – 200,000 | 1,000 |
| 200,001 – 300,000 | 2,000 |
| 300,001 – 400,000 | 3,000 |
| 400,001 – 500,000 | 4,000 |
| … | เพิ่มทีละ 1,000 บาทต่อทุก ๆ 100,000 บาทของช่วงราคา |

**หลักการคิดอัตโนมัติ:** `tierFee = 500 + floor((closePrice - 1) / 100_000) * 500` สำหรับ closePrice ≥ 1 (ปรับ cap สูงสุดใน config ถ้าต้องการ)

### คำแนะนำ

- **เริ่ม pilot ด้วย Model B (เรทราคา)** — เข้าใจง่าย คาดการณ์ได้ สื่อสารกับผู้ขายรถบ้านได้ดี
- เก็บ Model A เป็นทางเลือกหลังมีข้อมูลปิดการขายจริงเพียงพอ

### เงื่อนไขเรียกเก็บ (แนวคิด)

- มี `closed_won` + listing `pending_sale`/`sold` + ราคาปิดที่ผู้ขายยืนยัน
- ไม่เรียกเก็บถ้าดีลล่มหรือ admin waive

## 11. Admin Settlement

### เมื่อปิดการขาย

1. สร้างรายการ **ค้างชำระ** (`settlementRecord`) จากเรทที่เลือก
2. ผูก `listingId`, `leadId`, `sellerId`, `closedPrice`, `feeAmount`, `feeModel`

### หน้า admin (MVP แนวคิด)

| คอลัมน์ | ความหมาย |
|---------|----------|
| ยอดที่ควรได้ | จากเรท / สูตร |
| ยอดที่รับจริง | รวมการชำระบางส่วน |
| ยอดค้าง | ควรได้ − รับจริง − ส่วนที่ waive |

### การดำเนินการ

- **ชำระบางส่วน** — หลาย `paymentLog` ต่อหนึ่ง settlement
- **waived / ปรับยอด / ยกเว้น** — รอบทดลอง pilot; ต้องมี `adminNote` + `adjustedBy`
- **payment log** — วันที่, จำนวน, ช่องทาง (โอน/เงินสด/อื่น ๆ ที่ admin บันทึก), หมายเหตุ

### ยังไม่ทำใน v5.6A

- Payment gateway, QR, ใบกำกับภาษีอัตโนมัติ
- ต้องมี agreement / ops ก่อนเปิดรับเงินจริง

## 12. Trust & Reward Points

### วัตถุประสงค์

- **Internal score ก่อน** — ยังไม่แสดงสาธารณะบนโปรไฟล์
- ใช้สำหรับโปรโมชัน / สิทธิพิเศษในอนาคต (ลำดับ inbox, ลดค่าบริการ pilot ฯลฯ)

### ระดับ (seller และ/หรือ buyer แยกกันได้)

| แต้มสะสม | ระดับ |
|----------|--------|
| 1,000 | Silver |
| 2,000 | Gold |
| 3,000+ | Platinum |

### มิติคะแนน (เก็บแยก)

| คีย์ | ตัวอย่างสัญญาณ |
|------|----------------|
| `buyerTrustScore` | consent ครบ, ไม่ถูกรายงานบ่อย, ตอบติดต่อ |
| `sellerReliabilityScore` | อัปเดต outcome ตรงเวลา, ปิดการขายยืนยัน, ไม่ spam reveal |
| `leadQualityScore` | งบ/offeredPrice สมเหตุสมผล, conversion |
| `nongaMatchScore` | ความพอใจจากการจับคู่ (feedback ภายหลัง) |

### หลักการ

- เพิ่ม/ลดจากพฤติกรรมที่ตรวจได้ ไม่จาก AI โหวตเดียว
- การรายงาน scam **ไม่ลดคะแนนทันที** — รอ admin
- ไม่แสดงตัวเลขให้ผู้ใช้ทั่วไปใน v5.6H แรก ๆ

## 13. Cost / API Considerations

### ทำไม lead/negotiation ถูกกว่า vision

- งานส่วนใหญ่เป็น **text** — ถามงบ, วิธีซื้อ, consent, สรุป lead
- ไม่ต้องวิเคราะห์รูปทุกข้อความ

### กลยุทธ์คุมต้นทุน

| วิธี | รายละเอียด |
|------|-------------|
| Deterministic templates | คำถาม/ตอบ consent, แจ้งรถขายแล้ว, ต่ำกว่า floor |
| จำกัดรอบต่อรอง | เช่น ไม่เกิน N รอบต่อราคาต่อ session แล้วสรุป |
| Lead snapshot ครั้งเดียว | หลัง consent ไม่ regenerate บ่อย |
| AI เฉพาะเมื่อจำเป็น | สรุปความต้องการยาว, คำถามซับซ้อน — รอบหลัง |
| ใช้ search ที่มี | `buyerScoredMarketplaceSearch`, marketplace chat search — ไม่เพิ่ม Gemini |

### ข้อห้ามรอบ blueprint

- **ห้ามเพิ่ม Gemini/API call จริง** ใน v5.6A และไม่เปิดใน deploy จนกว่า phase ที่กำหนดชัด

## 14. Risks & Guardrails

| ความเสี่ยง | Guardrail |
|------------|-----------|
| PDPA / ข้อมูลส่วนบุคคล | Consent ชัด, บันทึกเวอร์ชัน, ลบตามนโยบาย (ออกแบบใน v5.6B) |
| ส่งเบอร์โดยไม่ยินยอม | Masked inbox + reveal หลังกดปุ่ม |
| น้องเอรับประกันผู้ซื้อจริง | Copy ห้าม “การันตี”; seller ตรวจสอบเอง |
| น้องเอรับปากแทนผู้ขาย | Negotiation guard + floor |
| เก็บเอกสารสำคัญ | ห้ามใน flow แรก + เตือนในแชท |
| Payment ก่อนพร้อม | ไม่เปิด gateway จน agreement/ops |
| ต้นทุน API | Templates + จำกัดรอบ; ไม่ Gemini ใน blueprint phase |
| Seller ดึงเบอร์ทุกคน | Reveal ทีละราย + outcome บังคับ |
| Marketplace สับสน | `pending_sale` ซ่อนทันที + แจ้งผู้ซื้ออื่น |

## 15. Phased Implementation Proposal

| Phase | รหัส | เนื้อหา | สิ่งที่ห้ามในเฟส |
|-------|------|---------|------------------|
