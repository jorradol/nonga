## Phase 1 security model: server-only

| ช่องทาง | Lead PII / queue |
|--------|------------------|
| **Cloud Run API** + Admin SDK | อ่าน/เขียน `buyerLeads`, `leadContactLogs` ได้ (ไม่ถูก rules จำกัด) |
| **Firebase client SDK** | **deny all** สำหรับ lead collections ทั้ง 3 |

### ทำไม admin client ก็อ่านตรงไม่ได้ในรอบนี้

- ลดความเสี่ยงรั่ว `contactPhone` ผ่าน Firestore console/client SDK
- Admin ใช้ **server routes / Admin SDK** เท่านั้น (สอดคล้อง masked seller queue API)
- เปิด client read ให้ admin ภายหลังได้เมื่อมี field-level rules + audit ชัดเจน

### ทำไม `buyerPurchaseProfiles` deny all

- Chat reuse ยังเป็น **client in-memory Map**
- Server profile repo ยังไม่ wire กับ chat API
- เปิด owner-read ใน rules ก่อน wire จะสร้างช่องว่าง sync ผิด

## ไฟล์ rules ที่แก้

| ไฟล์ | บทบาท |
|------|--------|
| `firestore.rules.draft` | **แหล่ง draft หลัก** ตาม `docs/firestore-storage-rules-v5.md` |
| `firestore.rules` | ใช้โดย `firebase emulators:exec` และ deploy staging — **sync lead block กับ draft** |

**ยังไม่ deploy:** ต้อง `firebase deploy --only firestore:rules` หลัง review + emulator pass

### Rules snippet (v5.6F.2)

```javascript
match /buyerLeads/{leadId} {
  allow read, write: if false;
}

match /leadContactLogs/{logId} {
  allow read, write: if false;
}

match /buyerPurchaseProfiles/{buyerUserId} {
  allow read, write: if false;
}
```

วาง **ก่อน** `match /{document=**}` เพื่อไม่ถูก override

## Tests

```bash
npm run test:v56f2-firestore-lead-rules
```

- **Static:** ตรวจ `firestore.rules` + `firestore.rules.draft` มี deny blocks และลำดับถูกต้อง
- **Emulator:** guest/member/seller/admin ไม่ read/write lead collections; smoke `dealerListings` / `users` ยังผ่าน

Pattern เดิม: `@firebase/rules-unit-testing` + `firebase emulators:exec` (ไม่เพิ่ม dependency ใหม่)
