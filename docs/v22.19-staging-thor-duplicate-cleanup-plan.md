## 2) Why automatic delete is blocked

Matching for the already-created duplicates may be ambiguous until operator inspects:

- New rows have **new** `car-import-{timestamp}-*` ids
- Fingerprints may collide with both the original Thor rows and each other
- Image fields on duplicates may be placeholder / empty / wrong id paths

**Rule:** do not delete if matching is ambiguous. Prefer merge into the **oldest** original Thor listing, then remove the duplicate only when clearly identified.

## 3) Identification procedure (staging, operator-controlled)

1. List Thor Auto dealer listings from staging Firestore `dealerListings` where `dealerId == "thor-auto"` (or equivalent admin inventory view).
2. Group by fingerprint: `brand + model + year + color + mileage + price` (and plate/VIN if privately present).
3. For each group with count ≥ 2:
   - **Canonical keeper** = oldest `createdAt` (prefer pre-reimport ids).
   - **Duplicate candidates** = newer `car-import-*` rows created at the re-import timestamp window.
4. Confirm each duplicate pair with at least one of:
   - exact full plate match (private field), or
   - exact VIN, or
   - exact fingerprint unique within dealer after excluding other groups
5. If more than one plausible keeper → **HOLD** that group; mark NEED REVIEW; do not delete.

**Do not log or paste full plate / VIN / phone / address into tickets or public docs.** Refer by listing id + brand/model/year only in audit notes.

## 4) Preferred merge then remove

For each clearly identified pair `(canonicalId, duplicateId)`:

1. Copy any **working** durable Firebase Storage image URLs from duplicate → canonical **only if** canonical still has ephemeral `/storage/listings/...` or empty/placeholder images.
2. Merge any newer valid CSV fields (price/mileage/description) into canonical using blank-safe rules (same as import upsert).
3. Set duplicate metadata on duplicate: `duplicateStatus: merged`, `duplicateCanonicalId: canonicalId`, `listingStatus: hidden` (or delete only after hide verified).
4. Prefer **hide + merge metadata** first; hard-delete only after marketplace count and chat retrieval look correct.
5. Record audit line (below).

After upsert fix is deployed, a **future** owner re-import should update canonical rows in place (count stable). Cleanup of the existing +3 should still be done once so count returns toward 13 (or the true unique Thor set).
