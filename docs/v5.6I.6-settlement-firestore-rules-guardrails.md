# v5.6I.6 — Settlement Firestore Rules & Emulator Guardrails

**สถานะ:** Rules logic ใน repo + emulator tests — **ยังไม่ deploy** `firestore.rules`  
**อ้างอิง:** v5.6I.5 (`9de741e`) — durable settlement persistence readiness

---

## เป้าหมายรอบนี้

บังคับใช้ **deny-all client access** สำหรับ collection การเงิน/settlement ก่อนเปิด Firestore persistence จริง โดย:

1. เพิ่ม explicit rules ใน `firestore.rules` (live file ใน repo)
2. ซิงค์ `firestore.rules.draft` ให้ตรงกัน
3. พิสูจน์ด้วย Firebase emulator ว่า **ทุก role** ถูก deny จาก direct client SDK
4. ยืนยันว่า access อนาคตต้องผ่าน **Cloud Run API + Admin SDK** เท่านั้น

---

## Audit ก่อนแก้ (v5.6I.5)

| ไฟล์ | settlement collections |
|------|------------------------|
| `firestore.rules.draft` | มี deny-all 3 collections (v5.6I.5) — **ไม่มี subcollection wildcard** |
| `firestore.rules` (live) | **ไม่มี** explicit settlement blocks — พึ่ง catch-all `match /{document=**}` เท่านั้น |

**ตัดสินใจ:** นำ deny-all blocks จาก draft เข้า **live `firestore.rules`** ใน repo + เพิ่ม subcollection wildcard `{document=**}` เพื่อกัน path ซ้อนในอนาคต

**ยังไม่ deploy** ไป Firebase จนกว่าลุง review รอบถัดไป

## Collections ที่ deny-all

| Collection | Rule path | Client access |
|------------|-----------|---------------|
| `successFeeRecords` | `/successFeeRecords/{recordId}` | `allow read, write: if false` |
| | `/successFeeRecords/{recordId}/{document=**}` | subcollection deny |
| `settlementAdjustments` | `/settlementAdjustments/{adjustmentId}` | deny |
| | `/settlementAdjustments/{adjustmentId}/{document=**}` | subcollection deny |
| `settlementAuditLogs` | `/settlementAuditLogs/{auditLogId}` | deny |
| | `/settlementAuditLogs/{auditLogId}/{document=**}` | subcollection deny |

วางก่อน `buyerLeads` blocks และก่อน catch-all

## เหตุผลที่ admin/seller ก็ห้าม client direct access

| Role | ห้าม direct Firestore | เหตุผล |
|------|----------------------|--------|
| buyer | ✓ | ห้ามเห็นข้อมูลการเงิน |
| seller / dealer | ✓ | แม้เป็นของตัวเอง — ต้องผ่าน API ที่ redact แล้ว |
| admin / superadmin | ✓ | บังคับ server-side audit, validation, ไม่ bypass API |

**Backend:** Cloud Run ใช้ Firebase Admin SDK — ไม่ถูกจำกัดโดย client rules (ปกติ)

## API-only access model

| ข้อมูล | Client path | Server path |
|--------|-------------|-------------|
| Admin revenue preview | — | `GET /api/admin/revenue/preview` |
| Manual adjustment | — | `POST /api/admin/revenue/adjustments` |
| Seller statement | — | `GET /api/my/revenue/preview` (redacted) |

Durable Firestore docs (เมื่อเปิด persistence) เขียน/อ่านผ่าน repository + Admin SDK เท่านั้น

## No buyer PII policy

- Rules test fixtures ใช้ synthetic uid/doc — **ไม่มี** `contactPhone`, buyer email, เบอร์ไทย
- Settlement durable model เก็บ `leadId` เท่านั้น — ไม่ duplicate PII ใน financial collections

## Deploy plan (staging — รอบถัดไป หลัง review)

1. รัน `npm run test:v56i6-settlement-firestore-rules` ผ่านใน CI/local
2. รัน `npm run test:v56f2-firestore-lead-rules` regression
3. `firebase deploy --only firestore:rules` ไป **staging project** เท่านั้น
4. Manual smoke: admin revenue preview API, seller statement API — ต้องยังทำงาน (ไม่ใช้ client Firestore)
5. ยัง **ไม่** เปิด `NONGA_SETTLEMENT_DATA_BACKEND=firestore` จนกว่า backfill plan ผ่าน

---

## Rollback plan (ถ้า rules deploy แล้วมีปัญหา)

1. `git revert` commit rules หรือ restore previous `firestore.rules`
2. `firebase deploy --only firestore:rules` ด้วย rules ชุดก่อนหน้า
3. Runtime ยัง memory — API revenue ไม่พึ่ง client Firestore อยู่แล้ว
4. ถ้า catch-all ถูกแตะโดยไม่ตั้งใจ — ตรวจ smoke tests users/listings/leads
