## 4. Gate B Evidence Collection Plan (Secret/Access/Boundary)

### 4.1 Secret Readiness Evidence (ไม่เปิดเผย secret)

- ใช้ placeholder และ metadata หลักฐานเท่านั้น (เช่น secret name, owner, rotation window, last audit time)
- ห้ามพิมพ์ค่าจริงของ key/token ลงเอกสาร, log, หรือ screenshot
- เก็บหลักฐานเป็น "sanitized screen capture" ที่ปิดทับทุกค่า sensitive

### 4.2 No Secret in Repo Proof

- รัน static scan กับเอกสาร/validation script เพื่อตรวจ pattern key/token
- หลักฐานที่เก็บ: output ของ validation ว่าไม่พบ secret pattern
- ระบุชัดเจนว่าไม่มีการเพิ่ม/แก้ env หรือ API key ใน phase นี้

### 4.3 Secret Storage Boundary Proof

- พิสูจน์เชิงแผนว่า secret อยู่ในระบบจัดการ secret ที่แยกจาก code repo
- เก็บหลักฐานเป็นแผน boundary diagram แบบ sanitized (ไม่แสดงค่า)
- แสดงหลักการ least privilege และ owner approval ก่อนใช้งานจริง

### 4.4 Access Boundary Proof

- ระบุ role matrix: owner/admin/operator เท่านั้นที่เข้าถึงขั้นเตรียมการ
- buyer/public ไม่มีสิทธิ์เห็นผล AI หรือ metadata ภายใน
- หลักฐาน: checklist สิทธิ์เข้าถึง + sanitized policy excerpt

### 4.5 Failure / Rollback Evidence ที่ต้องเตรียม

- สถานการณ์ fail ที่ต้องรองรับ: missing secret, invalid secret reference, unauthorized access
- ต้องมี stop condition: ถ้า proof ของ secret boundary ไม่ครบ = no-go
- ต้องมี rollback intent record ว่า revert สู่ deterministic-only path ทันที

## 5. Gate C Evidence Collection Plan (Admin-only Dry-run Readiness)

### 5.1 Admin-only Dry-run Readiness Evidence

- รวบรวมหลักฐานว่า scope การทดสอบในอนาคตจำกัดเฉพาะ admin/operator allowlist
- ไม่มีการเปิด buyer-facing หรือ public-facing AI path
- หลักฐานเป็น policy checklist + sanitized config intent (ไม่ใส่ค่าจริง)

### 5.2 Admin-only Boundary Proof

- ยืนยัน boundary ระหว่าง admin panel กับ buyer/public experience
- แสดงหลักฐานว่า buyer/public ไม่ได้รับ AI-generated output
- หลักฐาน: test matrix ระดับเอกสาร + expected deny/skip outcome

### 5.3 No Buyer-facing Exposure Proof

- ระบุชัดว่า output AI (หากมีในอนาคต) ต้องไม่แสดงใน buyer/public UI ระยะนี้
- หลักฐาน: negative checklist ว่า buyer/public scenarios ต้องเห็น deterministic เท่านั้น

### 5.4 Deterministic Source-of-Truth Proof

- ยืนยันว่า search/lead/consent/queue/inventory authority ยังเป็น deterministic
- AI ในอนาคตเป็นเพียง assistive layer ที่ override deterministic ไม่ได้

## 6. Budget / Quota Evidence Collection Plan (No Live Activation)

หัวข้อหลักฐานที่ต้องเตรียม:

- daily cap evidence (เพดานรายวันที่ owner ต้อง approve)
- per-run cap evidence (เพดานต่อการเรียกแต่ละครั้ง)
- timeout cap evidence (เพดานเวลา execution)
- emergency stop evidence (หยุดใช้งานฉุกเฉินได้ทันที)
- cost/quota baseline evidence (baseline ก่อนใช้งานจริง)
- owner-approved spending limit evidence (วงเงินที่อนุมัติล่วงหน้า)

รูปแบบหลักฐาน:

- policy sheet แบบ sanitized
- approval checkbox ที่ลงนามโดย owner
- static validation output ที่ยืนยัน "ยังไม่เปิดใช้งานจริง"

## 7. Kill Switch Evidence Collection Plan (No Real Gemini)

### 7.1 Switch Concept (เชิงแนวคิด)

- ใช้แนวคิด global kill switch + scoped emergency switch
- ไม่มีการ bind secret จริงในรอบ v8.1
- ไม่มีการส่งคำขอไปยัง Gemini จริง

### 7.2 Dry-run Verification Steps

1. ตรวจเอกสารว่าระบุ switch policy ครบ
2. ตรวจว่าไม่มี activation command
3. ตรวจว่าไม่มี env/key mutation
4. ตรวจว่า fallback deterministic ถูกระบุเป็น default safe behavior

### 7.3 Evidence ที่ต้องเก็บ

- sanitized screenshot ของ checklist
- validation output
- git status
- owner review mark: pass/hold/no-go

### 7.4 Stop Condition

- หากพิสูจน์ไม่ได้ว่า kill switch ทำหน้าที่หยุด flow ได้ (เชิงแผน) = no-go สำหรับรอบถัดไป

## 8. Fallback Deterministic Evidence Collection Plan

ต้องมีหลักฐาน fallback สำหรับกรณี:

- AI fail
- timeout
- blocked output
- unsafe output
- hallucination risk
- policy uncertainty

Expected evidence:

- แต่ละกรณีต้องระบุ expected deterministic fallback outcome
- ต้องพิสูจน์ว่า buyer/public ยังได้คำตอบจาก deterministic authority
- ต้องไม่มีการ fabricate ข้อมูลรถนอก inventory

## 9. Logging / Redaction Evidence Collection Plan

### 9.1 Allowed Sanitized Logs

- request-id / trace-id ที่ไม่โยงกลับ PII โดยตรง
- status code และ reason code แบบ aggregated
- timestamp และ feature flag state แบบไม่เปิดเผยข้อมูลลูกค้า

### 9.2 Forbidden Logs

ห้ามบันทึกหรือเผยแพร่ข้อมูลต่อไปนี้ในหลักฐาน:

- phone number
- full plate number
- full VIN
- internal price
- wholesale price
- raw owner data
- raw lead data

### 9.3 Sample Sanitized Evidence Format

- `trace_id=dr-xxxx`
- `flow=deterministic_fallback`
- `reason=policy_uncertainty`
- `result=buyer_safe_response`
- ไม่มี field ที่เป็น PII หรือข้อมูลราคาภายใน
