# v5.6E.1 — Buyer Purchase Profile Reuse

**Status:** Staging MVP (in-memory profile store)  
**Depends on:** v5.6D.1 buyer lead capture + consent modal (phone per submit)

## Goal

When a signed-in buyer has previously submitted lead basics, starting lead capture on **another car** should offer to reuse name, purchase method, budget/offer, and contact window — without retyping everything in chat.

**Phone is never stored in the purchase profile.** Each new lead still requires entering phone in the consent modal and explicit confirm for that listing round.

## Stored fields (per `buyerUserId`)

| Field | Stored |
|-------|--------|
| displayName | Yes |
| purchaseMethod | Yes |
| budgetMin / budgetMax / offeredPrice | Yes |
| preferredContactWindow | Yes |
| contactPhone | **No** |

Profile is written after a **successful** modal submit (`saveBuyerPurchaseProfileFromDraft`).

## Storage

- **In-memory** `Map<buyerUserId, BuyerPurchaseProfile>` in `buyerPurchaseProfile.ts`
- Same limitations as buyer leads: restart/redeploy/multi-instance resets profiles
- **No Firestore rules/migration** in this phase
- Guest users have no cross-session profile until they submit while signed in

## Flow

1. Buyer taps **ให้เจ้าของรถติดต่อกลับ** on a car card.
2. If `getBuyerPurchaseProfile(uid)` exists → stage `reuse_profile_choice`, chat summary + buttons:
   - **ใช้ข้อมูลนี้ต่อ** → `ready_for_modal` + open consent modal (empty phone field)
   - **แก้ไขข้อมูล** → `collecting` with fields prefilled; edit in chat then usual modal path
3. If no profile → v5.6D.1 collecting flow unchanged.
4. Modal submit still requires login, phone, and consent checkboxes for **this** listing.

## Privacy guardrails

- No auto-submit; reuse only advances to modal after explicit **ใช้ข้อมูลนี้ต่อ**
- No phone in profile object or reuse summary UI
- Seller still receives lead only via existing consented API POST for that round
- Payment / admin settlement / full seller reveal unchanged
