## 3. Runtime-Proof Plan Catalog (Planning Only)

### 3.1 Secret Wiring Proof Plan

- **objective:** พิสูจน์ว่า secret wiring ถูกต้องใน environment ที่อนุญาตเท่านั้น โดยไม่เปิดใช้งาน buyer-facing flow
- **prerequisite:** owner อนุมัติ execution window, มี redacted checklist, และมี operator ที่ได้รับสิทธิ์ admin-only
- **evidence to collect:** redacted env mapping checklist, proof ว่า config flag ถูกผูกเฉพาะ admin-only shadow path, และ evidence ว่าไม่มีการฝัง secret ใน source
- **acceptable evidence:** checklist ครบ, review log ของ owner/operator ครบ, และไม่พบ secret leak pattern
- **failure/blocker condition:** พบ missing secret mapping, พบ secret อยู่ผิดขอบเขต, หรือพบ risk ต่อ privacy/security
- **rollback/stop condition:** หยุดทันทีเมื่อพบ mapping mismatch หรือพบสัญญาณ secret exposure; revert กลับสู่สถานะ non-activation baseline
- **owner sign-off requirement:** ต้องมี owner sign-off แบบ traceable ก่อนขั้น execution ใดๆ

### 3.2 Budget/Quota Cap Proof Plan

- **objective:** พิสูจน์ว่า budget/quota cap บังคับเพดานการเรียกใช้งานได้ก่อนเริ่ม shadow runtime จริง
- **prerequisite:** มี cap policy ที่ owner รับรอง, มี threshold matrix, และมีผู้รับผิดชอบ monitor
- **evidence to collect:** cap configuration snapshot, simulated cap breach scenario plan, และเอกสาร alarm routing
- **acceptable evidence:** cap threshold ตรวจสอบย้อนหลังได้, simulated scenario แสดงการหยุดใช้งานได้, และ owner ยืนยันว่า cap เพียงพอ
- **failure/blocker condition:** cap ไม่ enforce, monitor ไม่ครอบคลุม, หรือเหตุการณ์ breach ไม่ถูกจับ
- **rollback/stop condition:** เมื่อ cap behavior ไม่ deterministic หรือ monitor ไม่พร้อม ให้หยุดและคง HOLD
- **owner sign-off requirement:** owner ต้องอนุมัติ cap matrix และ breach response plan ก่อนเดินขั้นต่อไป

### 3.3 Kill Switch Proof Plan

- **objective:** พิสูจน์ว่า kill switch ปิดเส้นทาง admin-only shadow ได้ทันทีเมื่อเกิดความเสี่ยง
- **prerequisite:** มี kill switch owner, operator runbook, และช่องทางประกาศ incident ภายใน
- **evidence to collect:** kill switch trigger checklist, timestamped drill record, และผลการตรวจว่าระบบกลับ deterministic-only path ได้
- **acceptable evidence:** drill มีหลักฐานครบ, ปิด path ได้ภายใน SLA ที่ตกลง, และไม่มี buyer-visible side effect
- **failure/blocker condition:** kill switch trigger ไม่ทำงาน, latency เกิน SLA, หรือยังมี shadow path ค้างอยู่
- **rollback/stop condition:** หาก kill switch ไม่สมบูรณ์ต้องหยุด execution candidate ทั้งหมดและคืนค่าเป็น non-activation state
- **owner sign-off requirement:** owner ต้องลงนามรับรองผล drill ก่อนอนุญาต runtime-proof execution

### 3.4 Admin-Only Boundary Proof Plan

- **objective:** พิสูจน์ว่า admin-only boundary แยกจาก buyer-facing/user-visible path อย่างชัดเจน
- **prerequisite:** มี role boundary matrix, route inventory, และ test scope ที่ไม่แตะ production
- **evidence to collect:** route/access matrix, deny-case checklist สำหรับ non-admin role, และ evidence ว่า shadow output ไม่ถูกส่งเข้าหน้า user
- **acceptable evidence:** non-admin เข้าไม่ถึง shadow path, buyer chat ไม่เห็น AI output, และ admin boundary review ผ่าน owner
- **failure/blocker condition:** พบช่องทางเข้าถึงโดย role ผิด, พบ output รั่วไปยัง buyer path, หรือมี ambiguity ด้านสิทธิ์
- **rollback/stop condition:** หยุดทันทีเมื่อ boundary แตกหรือมีโอกาส buyer-visible; คง deterministic response จริงเป็นหลัก
- **owner sign-off requirement:** owner ต้องลงนามรับรอง boundary evidence ก่อนปลด HOLD

### 3.5 Fallback Behavior Proof Plan

- **objective:** พิสูจน์ว่า fallback behavior กลับไป deterministic response จริงได้ทุกกรณีเสี่ยง
- **prerequisite:** นิยาม fallback matrix ชัดเจน, กำหนด failure class ครบ, และมี scenario owner-reviewed
- **evidence to collect:** fallback scenario checklist, expected deterministic response mapping, และ incident note template
- **acceptable evidence:** ทุก scenario ที่กำหนด fallback ได้ตรง expected behavior และไม่มีผลกระทบต่อ lead flow guard
- **failure/blocker condition:** fallback ไม่ครอบคลุม, fallback ไม่ deterministic, หรือแทรกแซง flow หลัก
- **rollback/stop condition:** หาก fallback มีความไม่แน่นอน ให้หยุดการเตรียม runtime ทั้งหมดและคงสถานะ HOLD
- **owner sign-off requirement:** owner ต้องอนุมัติ fallback matrix และ deterministic mapping ก่อน execution

### 3.6 Logging/Redaction Proof Plan

- **objective:** พิสูจน์ว่า logging/redaction ไม่เผย PII หรือ secrets ระหว่างการเก็บหลักฐาน shadow readiness
- **prerequisite:** มี redaction policy ล่าสุด, field sensitivity map, และ reviewer สำหรับ privacy
- **evidence to collect:** redacted log sample checklist, PII scan report, และหลักฐานว่า secret/token ถูก mask
- **acceptable evidence:** log ผ่านเกณฑ์ redaction, ไม่พบข้อมูล phone/plate/VIN เต็มโดยไม่จำเป็น, และ privacy reviewer เห็นชอบ
- **failure/blocker condition:** พบ PII/secrets ใน log, redaction rule ไม่ครอบคลุม, หรือ evidence trace ไม่เพียงพอ
- **rollback/stop condition:** เมื่อพบ data leak ให้หยุดทันที, isolate artifact, และคง non-activation posture
- **owner sign-off requirement:** owner และ privacy reviewer ต้องลงนามร่วมก่อนอนุญาตขั้นต่อไป

### 3.7 Deterministic Authority Proof Plan

- **objective:** พิสูจน์ว่า deterministic flow remains source of truth และยังเป็น authority เหนือ shadow result เสมอ
- **prerequisite:** นิยาม deterministic authority contract ชัดเจนและ owner รับทราบ
- **evidence to collect:** contract checklist, override-precedence proof, และ scenario ที่ยืนยันว่า shadow result ไม่เปลี่ยน deterministic response จริง
- **acceptable evidence:** deterministic precedence ทำงานครบทุกกรณีที่กำหนด, ไม่มี runtime activation ต่อผู้ใช้จริง, และ evidence audit ได้
- **failure/blocker condition:** shadow result สามารถเปลี่ยนผลลัพธ์จริง, หรือ deterministic guard ถูก bypass
- **rollback/stop condition:** พบ authority drift เมื่อใดให้หยุดทันทีและคืนค่า deterministic-only control
- **owner sign-off requirement:** owner ต้องลงนามรับรอง deterministic authority proof ก่อนพิจารณา GO สำหรับ preparation phase ถัดไป
